# @deepseek-ai/dsh-auto-review

[English](README.md) | 中文

针对受审批约束的工具请求进行策略驱动的安全审查。本插件作为一个 `approval/request` 应答者挂载：先让一个专门的审查子代理对请求的风险进行分类，再把审查者的判定通过配置好的规则策略映射为 `allowed-once`、`rejected` 或委托出去的结果。审查通过 `enabled` 显式开启；关闭时或任一环节失败，请求都会通过委托给下一个应答者而以拒绝方式关闭。

审查者是受限的子代理：它接收工具名、原因以及该请求暴露出的威胁类别，自身不持有任何工具，返回结构化的 `{ risk, decision, reason? }` 判定。`decision` 是审查者的原始建议；应答者再通过策略 `rules` 对最终判定进行裁决，因此 `deny` 建议与策略 `allow` 规则都能对请求形成约束。

每次审查都会追加一条只写日志的 `approval/review` 会话事件，记录最终的 `risk`、`decision` 与判定结论，从而在不让审查提示进入模型可见上下文的前提下，保证审计轨迹完整。[auto-review-invariant](../../../.agents/notes/implemented/feature/2026-08-24-auto-review.zh.md) 包拥有一个运行时不变量，用于校验这些记录只携带已知分级。

## 策略映射

`ReviewPolicy` 包含一个 `rules` 列表与一个 `noMatch` 兜底。`decide()` 将每条规则的 `categories` 和 `minRisk` 与请求分类出的类别、以及审查者的 `risk` 进行比较；第一条匹配规则的 `decision` 即为最终判定，无匹配时回退到 `noMatch`。规则 `decision` 为 `allow` 时映射为 `allowed-once`，`deny` 映射为 `rejected`，其余情况委托出去。`Reviewer` seam 可替换，因此策略逻辑可以独立于子代理传输进行单元测试。

## 模型体验

### 审查上下文贡献

#### 模型会看到什么

什么都不看到。审查子代理在子会话中运行，它的提示、工具清单与结构化判定永远不会进入父代理的上下文。`approval/review` 只写日志；模型只会看到发起请求的消费方最终允许或拒绝的工具结果，与不经过审查直接走审批 seam 时完全一致。

#### Token 影响

审查本身在父上下文中占零 token。审查子代理在自己的会话中消耗模型 token，其规模受限于该子代理自身的完成；这个开销对父代理不可见。

#### KV 缓存影响

审查不改变父代理的前缀，因此既有 KV-cache 条目仍然有效。审查工作在子代理中完成，不会扰动父代理缓存的提示。

## 已知局限与待办工作

- **策略对每次审查都是静态的** —— 规则是固定配置，而非可学习或按会话生效的策略；规则撤销与授权记忆尚未实现。
- **审查者是通用型子代理** —— 它通过收窄工具集与结构化输出加以约束，但没有专门的威胁分析画像或校准过的风险模型；严重程度校准尚未实现。
- **审查不覆盖审批服务** —— 强制执行仍由 `ApprovalPolicy` 负责；auto-review 只决定一个本已合格的请求的结果，无法把 `'never'` 请求变成交互式提示。
- **不审查模型视野之外的风险** —— 审查者只能看到工具名与原因，无法检查实际的工具参数或文件系统影响；参数级沙箱仍是各 sandbox 包的职责。
