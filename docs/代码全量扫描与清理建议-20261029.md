## 一、算法与性能：优先处理

### A01 · P1：语义搜索先取全局 Top-K 再过滤，可能返回错误的空结果

位置：[searcher.ts:52](/Users/zsn/Documents/毕设/packages/runtime/fs/tool-fs-semantic-search/src/searcher.ts:52)、[vector-store.ts:134](/Users/zsn/Documents/毕设/packages/runtime/fs/tool-fs-semantic-search/src/vector-store.ts:134)。

当前先从全库取 `3 × topK`，之后才按 file/language/type 过滤。过滤范围内的最佳结果不在全局候选里时，就会被遗漏。已直接加载当前 TS 源码复现：四个相同向量，对应 `a.ts/b.ts/c.ts/target.ts`，`topK=1`；不加过滤返回 `a.ts`，加 `file: target.ts` 返回 `[]`。

建议把过滤谓词传入 VectorStore，在计算相似度和入堆之前排除不合格 chunk。保持现有 MinHeap，避免退回全量排序。回归覆盖目标存在/不存在、混合语言、相同分数和过滤后不足 K 条。

### A02 · P1：Markdown 稳定块切分对连续列表是 O(L²)

位置：[markdown-stream-blocks.ts:75](/Users/zsn/Documents/毕设/src/features/chat/markdown-stream-blocks.ts:75)、[AgentMessageMarkdown.tsx:71](/Users/zsn/Documents/毕设/src/features/chat/AgentMessageMarkdown.tsx:71)。

每行列表都触发 `slice/join` 全部已读前缀，`canSeparateBlock` 再 split/map 扫描前缀，最后因仍属于同一个列表而不切分。流式文本每次增长都会从头执行。主控复测 1,000/2,000/4,000 行列表，三次运行中的最快单次耗时约 **41/135/541 ms**；4,000 行输入仅约 47 KB。

建议用列表缩进、表格、引用和 fence 状态实现单次扫描，并仅重新解析仍在增长的尾块。保留 Markdown 边界语义；验证长列表、嵌套列表、引用、表格、代码块、引用链接和逐段追加。优先消除平方扫描，再考虑进一步增量解析。

### A03 · P2：工作区索引冷缓存没有合并并发构建

位置：[workspace-index.mjs:79](/Users/zsn/Documents/毕设/backend/workspace-index.mjs:79)。

首查和五秒 TTL 过期时，每个并发 `list()` 都独立构建索引；每次又串行 lstat 所有条目。用 mock 文件系统计数复现：**8 个同时查询、3,000 个条目，产生 8 次 readdir 和 24,000 次 lstat**。

建议按 root + generation 共享在途 Promise，完成或失败后释放；保留切工作区时阻止旧结果污染缓存的逻辑。搜索结果达到 limit 后可提前停止收集。验证同时冷查只建一次、切换 root、失败后重试和 TTL 失效。

### A04 · P2：Cursor OAuth 冷读取/刷新会重复启动凭据 helper

位置：[oauth-token-cache.mjs:30](/Users/zsn/Documents/毕设/packages/provider-bridge-transport/oauth-token-cache.mjs:30)、[index.mjs:459](/Users/zsn/Documents/毕设/packages/provider-bridge-transport/index.mjs:459)。

缓存只保存完成的 token，不保存加载中的 Promise。主控复现 **8 个并发冷 get 触发 8 次 loader**；生产 loader 会启动 Bun 子进程读取 OAuth 凭据。

建议按 provider 合并在途请求，用 generation 防止 invalidate 后旧请求重新填入缓存；每个调用方的取消要独立处理。验证刷新失败、重试、invalidate 竞态和独立取消。Google OAuth 当前读取账户相关 snapshot，不能机械套用同一全局缓存。

### A05 · P2：Antigravity SSE 长行被反复扫描

位置：[google-antigravity-adapter.mjs:606](/Users/zsn/Documents/毕设/packages/provider-bridge-transport/google-antigravity-adapter.mjs:606)。

每个网络 chunk 到达后都 split 尚未结束的整条长行，并再次 `Buffer.byteLength(buffer)`。长 SSE JSON 被拆成小 chunk 时，累计扫描量接近 O(B²/chunkSize)。只读合成有效 SSE、16 KiB 分片，1/2/4/8 MiB 分别约 **10/24/80/316 ms**。

建议增量统计字节数和换行游标，分片暂存，完整行只合并一次。保留 16 MiB 上限；验证跨 chunk UTF-8、CRLF、多行 data、终态、取消和大小边界。

### A06 · P2：代码分块对每个 chunk 再扫描整份文件的 imports

位置：[chunker.ts:103](/Users/zsn/Documents/毕设/packages/runtime/fs/tool-fs-semantic-search/src/chunker.ts:103)。

每产生一个 JS/TS chunk 都执行 `extractImports(content)`，成本是 O(文件长度 × chunk 数)。源码实验：1,000 个函数、35.9 KB，执行 1,000 次全文扫描，约 26 ms；2,000 个函数、72.9 KB，执行 2,000 次，约 95 ms。

建议每文件提取一次 imports，共享不可变结果。验证任意 chunk 数量下 imports 只扫描一次，同时保持 chunk 内容、顺序和元数据一致。

### A07 · P2：聊天每行过滤全部工具历史，O(M × T)

位置：[dshTranscriptMessages.ts:32](/Users/zsn/Documents/毕设/src/features/dsh-runtime/dshTranscriptMessages.ts:32)、[MainConversation.tsx:543](/Users/zsn/Documents/毕设/src/features/chat/MainConversation.tsx:543)。

父组件逐条消息调用 `dshToolHistoryForMessage`，每次 filter 全量工具行。即使子 Message 的 memo 生效，父组件的遍历与数组分配仍然发生；流式更新也会触发。

建议一次按 turn 分桶，用稳定桶引用让每行 O(1) 查询，整体趋近 O(M+T)。保留 turn=0、最新 turn、无 turn 旧消息和实时 traces 的归属规则；用多轮多工具历史验证。

### A08 · P2：重试/编辑关系在消息循环内反复查找，最坏 O(M²)

位置：[MainConversation.tsx:552](/Users/zsn/Documents/毕设/src/features/chat/MainConversation.tsx:552)。

每条助手消息都反向寻找用户，再反向寻找前一助手；用户响应也向前重复搜索。连续助手消息、上下文行或压缩行较多时，多次扫描同一个前缀。

建议前向/后向两遍生成 previousRealUser、previousAssistant、firstResponse 关系表，渲染按索引查询。验证 steer、compaction、失败消息以及编辑/重试的锚点不变。

### A09 · P2：稳定回调和数组缓存不淘汰旧消息

位置：[stable-callbacks.ts:13](/Users/zsn/Documents/毕设/src/features/chat/stable-callbacks.ts:13)、[stable-messages.ts:45](/Users/zsn/Documents/毕设/src/features/chat/stable-messages.ts:45)。

两个 Map 只有 set，没有 delete。MainConversation 跨会话保持挂载，key 包含 message.id；已离开的会话、被 rewind 删除的消息仍被持有，回调闭包还可能保留旧消息数组。

建议按 conversationId 重建这些缓存，或淘汰当前有效消息集合外的 key。不要为清缓存盲目重挂整个聊天组件而丢失滚动位置。验证多会话切换、删除和回退后缓存规模收敛，同时保留 callback identity 的稳定性。

### A10 · P2：SQLite FTS 在新增事件后的搜索中全量重建会话索引

位置：[session-query-sqlite/index.ts:881](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query-sqlite/src/index.ts:881)、[index.ts:891](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query-sqlite/src/index.ts:891)、[index.ts:602](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query-sqlite/src/index.ts:602)。

Session.events append 后更换引用，observeLive 缓存失效；重新深拷贝全部事件、fold、生成搜索文档、JSON 序列化并 SHA256，再删除该会话全部 FTS 文档并重新插入。即使新增事件不产生搜索文本，也会走观察重建。变化后搜索成本随整份日志增长。

建议按 seq 增量观察和写入，replacement 只更新受影响文档，保留 cursor generation 的一致性语义。现有 warmed 10k-message probe 已通过，但只证明“不变日志重复查询”可复用，不能证明 append→search 是增量的；应补该场景。

### A11 · P2：只读一条事件前先深拷贝全日志

位置：[session-query/index.ts:322](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query/src/index.ts:322)、[corpus.ts:292](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query/src/corpus.ts:292)。

`readEvent({before:0, after:0})` 仍先 load 并 clone 全部 live events，最后才切窗口，并对返回事件再次 snapshot。单条读取也承担 O(全日志字节数) 时间和临时内存。

建议 live 窗口读取先借用已冻结源、只克隆最终窗口；冷日志读取限制独立保留。验证返回对象不能反向修改源、seq 边界和取消行为。

### A12 · P2：FTS 每次复核两遍持久化目录，冷日志 inspect 串行

位置：[session-query-sqlite/index.ts:497](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query-sqlite/src/index.ts:497)、[index.ts:508](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query-sqlite/src/index.ts:508)、[index.ts:514](/Users/zsn/Documents/毕设/packages/runtime/session-query/session-query-sqlite/src/index.ts:514)。

建议用可靠 manifest/revision catalog 降低稳定目录的重复读取，冷 inspect 使用有限并发。第二次快照承担一致性验证，不能直接删除；验证并发改文件、服务切换、取消、损坏日志及重试上限。

### A13 · P2：会话小更新成本随所有历史正文增长

### A14 · P2：每条 usage 记录重新聚合并排序全部 buckets

### A15 · P2：语义索引是模块全局 Map，缺少容量预算与实例隔离

### A16 · P2：DAG 按树递归，重复展开共享后继

位置：[SubagentSessionTree.tsx:10](/Users/zsn/Documents/毕设/src/features/orchestration/SubagentSessionTree.tsx:10)。
