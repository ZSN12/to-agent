# 成本感知模型路由与能力作品集（设计思路）

> 版本：2026-09-27  
> 状态：已实现用户级作品集与额度路由；默认模板不假定任何人的套餐
> 关联：《毕设设计方案-多智能体编程系统.md》§7.2、《docs/模型价签自动同步.md》、`pricing/registry.json`、`electron/backend/orchestration-policy.mjs`、`src/features/models/RoutingPortfolioSettingsPanel.tsx`

---

## 1. 动机与原则

TaskWeaver 的编排目标仍是：

> 在质量约束下，最小化**成功完成一次任务**的预期总成本（含重试、升级、协调开销），而不是单次 API 报价最低。

用户侧往往同时持有多种**计费形态**：

| 形态 | 典型例子 | 路由含义 |
|------|----------|----------|
| 按量计费 | 官方 API、部分中转 | 用 `input_price` / `output_price` 估算边际成本 |
| 订阅／打包 | Cursor、Codex、反重力（Antigravity）等桌面客户端 | 订阅覆盖内没有单次 API 账单，但账号额度仍可能稀缺；按任务适配和额度周期决定是否倾向使用 |
| 时段差异 | DeepSeek 官方工作日白天加价等 | 在「贵时段」对按量模型降权或换通道 |

因此，分配器不能仅靠 UI 上的「低／中／高」三档或固定 `tier` 排序；需要一份用户可维护的**能力作品集（Routing Portfolio）**，把「任务适合谁」「当前哪条通道更划算」写清楚，再由规则打分产出可解释的 `routeReason`。

**与门控的关系（不变）**：入口 `RuleGate` 仍**不调用**任何 LLM；作品集与成本打分仅用于：

- 多智能体路径上的 **子任务分配**（`AllocationRouter` / `selectModelForTask`）；
- 可选：单 Agent 下用户未手动锁模时的**默认执行模型**（产品开关，非论文必需）。

## 2. 界面：模型只展示「名字」，通道进设置

### 2.1 主界面（对话、Composer、DAG 节点摘要）

- **只展示**用户可读的 **displayName**（如「Gemini 3.8 Flash」「Composer 2.5」「DeepSeek V3.2」）。
- **不展示**提供方通道标签（官方 API、OpenCodex、`cursor/`、`google-antigravity/` 等）——避免用户每次选模型时做「渠道经济学」。
- 当前实际使用的 `model_id` 可在「会话详情 / 轨迹」中展开查看，供调试与论文截图。

### 2.2 设置（模型管理）

- **已添加模型**：扁平列表（用户显式添加的条目），**取消**列表上的「低／中／高」质量档展示。
- **通道与凭据**：在「高级」或按提供方折叠的区域配置（API Key、本机 `ocx`、OAuth 说明等）；同一逻辑能力若有多通道，在设置里并列，主界面仍是一个 displayName 或用户自选默认通道。
- **参与自动分配**：保留 `enabledForAllocation`（或等价开关），让用户声明「这条模型允许编排器选用」。

### 2.3 与现有实现的关系

- 今日 UI 仍从 `profile.tier` 或成本推断渲染「低／中／高」（`src/features/models/format.ts`）——属**待移除**的产品债。
- `ModelProfile.tier` 在数据层可保留为**内部分档**（PolicyGate、冷启动先验），但**不对用户暴露三档文案**。

## 3. 能力作品集（Routing Portfolio）

作品集是**当前用户**维护的 JSON，与 `pricing/registry.json`（自动价签）**互补**。每位用户的配置单独保存；仓库默认模板不内置任何人的模型订阅、免费渠道或账户额度策略：

| 数据源 | 职责 |
|--------|------|
| `pricing/registry.json` + adapters | 按量单价、上下文窗口、同步审计（见《模型价签自动同步》） |
| **routing-portfolio**（`userDataPath/taskweaver/routing-portfolio.json`） | 当前用户的订阅、免费模型、额度池映射、任务—模型亲和、时段规则、displayName 映射 |

### 3.1 建议结构（示意）

默认模板为空白配置。当前用户按自己的实际渠道填写 `subscriptions`、`free_model_patterns`、`quota_cycles.policies` 和 `balance_policies`；`provider_id + resource_id` 对应 UsageSource 实际返回的资源，`match_model_keys` 指定额度池影响哪些模型/接入渠道。不同用户可以有完全不同的模型、套餐和周期。

```json
{
  "version": 2,
  "subscriptions": [
    {
      "id": "my-subscription",
      "label": "我的编程订阅",
      "prefer_models": ["my-provider/*"],
      "marginal_cost": 0
    }
  ],
  "free_model_patterns": ["my-free-provider/*"],
  "quota_cycles": {
    "enabled": true,
    "policies": [
      {
        "provider_id": "my-provider-account",
        "resource_id": "weekly-window",
        "match_model_keys": ["my-provider/*"],
        "rollover": false,
        "use_before_reset": true,
        "exhausted_action": "exclude"
      }
    ]
  },
  "balance_policies": [
    {
      "provider_id": "my-api-account",
      "resource_id": "balance",
      "match_model_keys": ["my-api-provider/*"],
      "unit": "usd",
      "low_balance_threshold": 5,
      "exhausted_action": "exclude"
    }
  ]
}
```

免费模型来自哪个渠道由用户自己配置，不要求它属于 OpenUsage。用户可用 `free_model_patterns` 明确标记；有可信、未过期的逐模型零价签时也可识别。缺失或低置信度价签不当作免费，额度池也不会自动推断到某个模型。

### 3.2 用户可编辑性

- 毕设演示：每位用户自己的 portfolio + 设置页「编辑作品集」；初始模板不预填订阅。
- 论文表述：作品集体现「用户对自己账号经济学与能力偏好的建模」，比黑盒三档更符合「可解释路由」。

## 4. 路由打分：像人一样选模型

### 4.1 输入

- `TaskSpec`（类型、风险标签、`acceptance`、是否只读等）；
- 用户**已添加**且 `enabledForAllocation` 的 `ModelProfile[]`；
- 合并价签后的 **边际成本**（订阅内 → 0；按量 → registry； surge → 加权）；
- 当前用户作品集：`task_affinity`、`subscriptions`、`free_model_patterns`、`metered_surge`、`quota_cycles`、`balance_policies`；
- 可选 `UsageSource` 的额度快照（原始单位、剩余值、重置时间、`fetchedAt`/`expiresAt`、`stale`、错误）；
- 可选：`historical_success`（审计日志回填）。

### OpenUsage 作为可选 UsageSource

已检查 GitHub 项目 [`robinebers/openusage`](https://github.com/robinebers/openusage)：它是独立的 macOS 菜单栏用量查看器，提供本地只读 `GET http://127.0.0.1:6736/v1/limits`，响应 schema 为 `openusage.limits.v1`，按 provider/resource 提供原始单位、已用/上限/剩余量、重置时间、`fetchedAt`/`expiresAt`、`stale` 和 errors。仓库 README 当前列出 Codex、Cursor、Antigravity、Claude、Copilot、OpenCode、OpenRouter、Z.ai 等支持项；具体字段依各服务可提供的数据而异。TaskWeaver 已接入这个只读接口：设置页通过现有 service/IPC 展示用量，DAG 路由在主进程读取 `/v1/limits`，只按当前用户明确配置的 `provider_id + resource_id + match_model_keys` 映射余额和额度，不复制 Provider 凭据读取逻辑。参照其 [README](https://github.com/robinebers/openusage) 与 [Local HTTP API 文档](https://github.com/robinebers/openusage/blob/main/docs/local-http-api.md)。

- OpenUsage 不安装/未运行时，TaskWeaver 仍可正常工作；额度回退为 `unknown`，继续按能力、价格与用户 Portfolio 路由。
- 尊重 `stale`、`expiresAt`、`fetchedAt` 和 errors。保留的最后成功快照可供设置页查看，但过期值不得参与额度加权。
- Provider 资源不一定一一对应 TaskWeaver 的 `model_id` 或账号，且可能代表共享池；只按明确配置的 `provider_id + resource_id + route mapping` 关联，禁止推断成模型级精确余额。
- API 只监听 loopback、仅提供 GET/OPTIONS，但允许浏览器跨域读取用量数值；TaskWeaver 应由 Electron 主进程访问固定地址、校验 schema 与响应大小，并确保用量快照不进入远程遥测。
- 额度来源表达消费状态，不提供模型能力真值；工具兼容性与能力仍由 ModelProfile/运行时验证。

### 4.2 硬约束（PolicyGate，先于打分）

与设计方案 §7.4 一致，例如：

- `security` / `auth` 等标签 → 禁止 `cheap` 直接写入；
- 无自动验收的写任务 → 需要 Reviewer 节点或更强执行档；
- 不支持 tools 的模型 → 不能担任带工具的 executor。

### 4.3 软打分（RuleRouter v1）

对每个可行候选计算标量分（越高越优），并生成**人类可读** `reasons[]`：

```text
score =
  w_task   * task_affinity_match(task, model, portfolio)
+ w_sub    * user_subscription_bonus(model)     # only this user's configured plans
+ w_free   * verified_free_route_bonus(model)   # per-model trusted price or this user's patterns
+ w_quota  * quota_remaining_and_reset(route)    # fresh user/account resource snapshot
+ w_balance* api_balance_adjustment(route)      # fresh balance resource, unit-aware
- w_meter  * metered_cost_estimate(task, model, now)
+ w_hist   * historical_success[task.type]
- w_risk   * underpower_penalty(task.risk, model.tier)
```

额度权重只针对当前用户显式映射的资源。新鲜快照用于优先余量更充足的额度池；只有确认不可结转且刷新时间明确，才额外考虑刷新窗口。耗尽策略可按用户配置为排除或降权；余额按单位和阈值单独处理。快照过期、资源缺失或语义未知时不推断余额。额度是**路由偏好**，不为消耗额度制造额外请求，也不改变任务质量门槛。

```text
quota_cycle_bonus = 0  if stale/unknown/unit-incomparable
quota_cycle_bonus = 0  if rollover != false
otherwise bounded(urgency(time_to_reset) * remaining_ratio * task_route_eligibility)
```

`task_route_eligibility` 只表示任务在能力与安全约束下适合该路线，不允许把不合格模型加回候选集合。毕设演示使用可复现的固定规则，不拟合复杂预测器。

**示例策略（与产品讨论一致）**：

| 场景 | 倾向 | 理由文案示例 |
|------|------|----------------|
| 仓库内搜索、读文件归纳 | 能胜任的低成本或免费模型 | 「检索型子任务，优先低成本」 |
| Code Review / 安全 | 用户标记为适合审查的强推理模型 | 「验收含 review，抬升推理能力」 |
| 中文文案、说明性写作 | 用户标记为适合该任务的模型 | 「匹配当前用户任务偏好」 |
| 难解 bug、跨模块 | 能力档位与上下文满足要求的模型 | 「hard_debug 任务适配」 |
| 用户配置的订阅模型 | 只在该用户的套餐规则匹配时加权 | 「匹配当前用户订阅」 |
| 用户配置的免费模型渠道 | 能力足以完成任务时优先考虑 | 「匹配当前用户免费渠道」 |
| 用户额度池余量充足 | 对映射到该额度池的模型有限加权 | 「额度快照显示该账户余量较多」 |
| 用户额度将耗尽或 API 余额偏低 | 按其策略降权或排除该路由 | 「关联额度池偏低/已耗尽」 |

输出与 §5.4 `RouteDecision` 对齐：`model_id`、`strategy`、`reasons`、`fallback`、`confidence`（可由分差归一化）。

### 4.4 与「三档」的替代关系

| 旧思路 | 新思路 |
|--------|--------|
| UI 低／中／高 | 用户只看 displayName；档位仅内部元数据 |
| `TASK_TIER_ORDER` 固定映射 | `task_affinity` + 打分 + PolicyGate |
| 仅 `costPerMillion` 排序 | `marginal_cost`（订阅 0 + surge + 按量） |

实现落点：`electron/backend/orchestration-policy.mjs` 的 `selectModelForTask` 由 tier 排序演进为 **portfolio 感知打分**；价签仍来自 `electron/backend/price-registry.mjs`。

## 5. 单 Agent 与多 Agent 的统一叙事

- **单 Agent**：用户手动选的模型优先；若开启「智能默认」，则用**同一套打分**选主执行模型（不增加 Planner 成本）。
- **多 Agent**：Planner 只产出 `TaskSpec[]`；每个节点独立 `RouteDecision`，从而在一条 DAG 上呈现「搜索用便宜、审查用强、实现用写代码偏好」的**异构路由**，便于论文案例与 Trajectory 展示。

## 6. 实现分期（与《TaskWeaver实施计划》对齐）

| 阶段 | 内容 | 验收 |
|------|------|------|
| **P1 展示** | displayName-only；去掉列表三档；通道折叠到设置 | 主界面无「低／中／高」、无渠道前缀 |
| **P2 作品集** | 用户级 `routing-portfolio.json` + 加载器；与 registry 合并 | 不同用户可设置不同渠道与套餐 |
| **P3 RuleRouter v1** | 打分 + `routeReason` 写入审计与 DAG UI | 固定 3 节点 DAG 显示不同模型与原因 |
| **P4 增强** | surge 窗口、OpenUsage 额度与余额路由已接入；historical_success、可选 LLMRouter 后续可选 | 过期/不可用额度安全降级；论文讨论材料 |

## 7. 论文与演示建议

- **案例 A**：同一需求「全链路强模型」vs「动态分配」——对比 Trajectory 中的 `model_id` 与估算 token 成本（各 1 次即可）。
- **案例 B**：显式展示两份不同用户 portfolio 的订阅/免费渠道偏好——修改配置前后 `reasons` 变化。
- **案例 C**：DeepSeek 贵时段——改系统时间或 mock `now` 展示降权。

**诚实局限**：订阅覆盖与是否结转可能以用户配置或服务方展示为准；OpenUsage 支持面、API 可用性和资源粒度受其版本及各提供商接口限制；`ocx` 目录漂移需重新同步；路由不保证等价于各客户端内手动点选的最优，只保证**可复现、可解释**。
