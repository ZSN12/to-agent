# 事件断流恢复验收（2026-10-03）

## 故障复现

测试直接运行当前部署的 Z Host 和真实 Agent，用本机 SSE 模型端点，无 GUI、无付费模型调用、无用户密钥或真实历史读写。只中断客户端 mux，不中止模型请求或 Host 进程。

修复前断流后原生 `sessions.list` 显示 Agent `running=true`，而 TaskWeaver `chat.isBusy` 已是 false，并立即 reject 首条 send。测试实际失败于 `transport loss must not falsely complete the Agent`。原生任务并未停止，接入层却声称结束。

原生接口 `packages/runtime/host/apiproxy/src/api/events.ts` 明确规定 `since` 暂不实现，恢复方式是重新打开 stream 并重新读取 history；原生客户端 Session 使用 seq 拼接历史/实时事件、清理新连接的队列基线。旧 TaskWeaver 桥接只重开连接，没有补齐断流期间的历史。

双会话用例加强到断言真实连接数后，还复现首次同时发送开两条 mux：`actual 2 / expected 1`。只检查两份答案会漏掉它，甚至会让第二条连接掩盖第一条断流。初始化现在共享一个尚未完成的 ready/mux handshake；用例要求一次初始连接、一次重连，并要求两会话都收到恢复状态。

## 改动

- 断流先进入 connection 状态，不清运行记录、不取消 Agent、不重发 prompt。
- 重连后分页读取原生缺失事件，按 seq 排序、去重，并沿用正常终止持久化逻辑。原生新连接队列基线代替旧镜像，重建断流期间的多轮边界。
- 原生运行列表用于确认是否仍执行；只有确认停止才释放运行状态。历史分页没有前进、接口失败或列表结构不合法时，不假报已恢复。
- 重连打开失败只由一个调用者安排重试，避免两个消费者竞争。连接打开超时会 abort 该连接，再启动下一次尝试。
- 活着的 Host 的健康检查暂时失败不再触发强制重启。
- 两会话同时首次请求共用初始化 promise，不再打开两个初始 mux 消费者。
- 修复 mux 的 8 秒初始握手计时器：原代码在 SSE 建连成功后仍让该计时器保持有效，8 秒后会 abort 健康长连接；该 abort 被当作主动取消处理，因此不会进入断流重连，随后模型回复只进 Host 历史、聊天桥接一直等不到 `turn/end`。现在握手成功或失败都会立即清除该计时器。
- 重试额度耗尽时首条 IPC 明确返回 `runContinues`，界面保留当前流、队列与运行标记，不把状态未知的调用当作已完成或执行失败落库。后续同步可重新建立连接并接回原任务。
- 原生终止事件的时间用于耗时统计，不能把历史补回的连接退避时间算作模型执行耗时。

## 已通过的真实 Host 场景

`scripts/test-z-mux-recovery.mjs` 主动把 session/event 重复交付，所有场景仍按 seq 消费一次：

1. 断流时仍在生成，重连后同一请求继续完成，只有一次 prompt 和一次 done。
2. Agent 在断流空档已经结束，补历史取得完整答案与终止，不挂起，不重执行。
3. 空档内接受并执行追问，两轮答案和 10/2 tokens 的供应商上报用量分别落库，只计一次。
4. 首次重新打开 stream 失败，仅有一个重试调用者，之后补回原答案。
5. 一次健康 RPC 失败不重启 Host、不重发任务，第二次检查后恢复。
6. 原生 cancel 在断流空档执行，恢复保留停止前正文和 interrupted 标记。
7. 连续五次健康检查失败，真实原生 Agent 仍执行；IPC 返回状态未确认，busy 保留，不写终止用量。显式读取状态后重连成功，原任务完成、只记录一次用量。
8. 重连打开卡住八秒，旧连接被 abort，下一次重连接回已经完成的任务，未重复执行。
9. 两个真实 Agent 同时运行，共享 mux 被切断；两边在空档结束，各自恢复一份答案和一份用量，不切换当前选择，不串会话、不重发任务。

另有长空闲专项回归：真实 Host 的压缩模型请求延迟 31 秒（超过原 mux 计时器），随后立即发普通追问；要求模型回复在 8 秒内通过当前实时 mux 收到 `turn/end`，早于 10 秒历史对账兜底。修复前重现失败：模型 HTTP 响应和完整 Host 历史均已存在，Host 报 `running=false`，但当前 mux 已无事件；修复后该专项通过。

分页 helper 测试执行生产函数，验证 170 个缺失事件跨三页拼回、保留工具 view、空缺口、不前进的分页及接口失败的封闭处理。

聊天桥接回归注入相同 approvalId/rpcId 的待处理审批和 question 重放，验证提示去重、回答 RPC 只发一次；审批清理定时器也校验 entry 身份，防止旧定时器删除新注册项。此前发现 `question/requested` 虽由 Z Runtime 支持，却没有接入 TaskWeaver，计划审阅可能一直等答案。现在通过 preload/IPC 将问题送到 composer，收齐结构化答案后发回原 RPC，并对重连重放去重。真实 Host 恢复套件在真实 mux 生命周期中注入受控审批与问题帧，跨断流重放并验证一次提示、一次回应；帧由测试代理构造，不等同于真实 `ask_user_question` 工具从模型调用到 Host 完成的端到端验收。

生产 hook 的无界面测试覆盖 `runContinues` 的晚到 IPC、连接恢复后清掉连接错误提示、保留部分输出与排队项，之后由正常 done 结束。

复现入口：`npm run test:z-recovery`。已纳入 `test:all`，但不代表本次跑完了整个 `test:all`。

## 验证边界

- 并发 DAG、原生 MCP、只读工具、失败轮次、队列、31 秒原生压缩、历史重启恢复等已有部署回归通过；用量、生产 hook、后端存储和构建回归通过。
- 这不是“网络永远不会失败”或“长任务普遍变快”的证明；使用的是受控端点，不是供应商性能测量。
- 进程被强杀后的存储刷新、Host 重启后所有投影/交互恢复，以及真实 Host 产生的授权/问题在断流时重放仍需分别故障注入。当前协议帧通过测试代理注入真实 Host mux；没有让模型实际调用 `ask_user_question` 或权限工具。
- 没有修改模型全轮时限，没有丢弃长会话历史，没有重新安装 `/Applications/TaskWeaver.app`。本轮改善的是连接故障时的真实性与恢复能力。
