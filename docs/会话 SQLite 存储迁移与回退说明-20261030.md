# 会话 SQLite 存储迁移与回退说明

更新时间：2026-10-30

本文说的是桌面后端 `ThreadStore` 中用于 UI 恢复的会话摘要、消息投影、任务与输出日志；它不替换 Z Runtime 的权威 session event JSONL。Runtime JSONL 仍由 `PersistenceCoordinator` 与 `session-persistence-jsonl` 管理，相关目录快照与查询改动单独验收。

## 存储结构

ThreadStore 现在使用用户数据目录中的 `taskweaver-threads.sqlite`，不再以 `taskweaver-threads.json` 作为运行时权威存储。SQLite schema version 为 2：`thread_summaries` 保存导航和筛选所需字段，`thread_bodies` 按 thread 保存消息、任务和输出日志；`store_meta` 保存 schema 版本和当前会话 ID。正文表保留一代上一版已提交正文，用于显式恢复单会话结构损坏。

连接使用 WAL、`synchronous=FULL`、10 秒 busy timeout 和外键级联。创建及事务提交会把数据库和 `-wal`/`-shm` 文件权限收紧到 `0600`。所有会话创建、修改、fork、归档和删除都由 `BEGIN IMMEDIATE` 事务协调；跨进程并发由 SQLite 写锁处理。

## 首次迁移

首次打开时，迁移器支持旧版单体 `taskweaver-threads.json`、旧摘要加 `threads/<id>.json` 正文布局，以及早期 `taskweaver-app-state.json` 单会话格式。旧源文件会保留原字节，并先创建独立备份：优先使用 `<源文件>.pre-sqlite.bak`；该路径已有不同内容时使用带内容摘要的备份名。旧版 V2 正文文件只读取，不改写。

SQLite 中的摘要、正文和迁移版本标记在同一事务里写入。提交前会核对会话数量、ID、当前会话、消息/task/日志内容及摘要；任一步报错都会回滚数据库事务，源文件仍留在原位。重复启动会识别已完成版本，不重复导入。schema v1 的 SQLite 库可以原地升级到 v2，旧正文保留，新的上一版正文列从空值开始。

## 正文损坏后的显式恢复

列表和搜索只读取摘要，因此一条正文损坏不会阻断其他会话的导航。读取损坏正文会报错；若上一版正文完整，错误会说明可恢复。恢复是显式操作，会把上一版正文恢复为当前正文、清除恢复槽，并同步修正 message count。当前正文有效时恢复命令会拒绝执行。恢复槽只保留最近一次正文提交，不能替代完整备份。

先停止桌面后端和其他写入进程，再备份整个 SQLite 文件组（数据库、`-wal`、`-shm`），然后运行：

```sh
pnpm run recover:thread-store -- "<USER_DATA_DIR>" "<CONVERSATION_ID>"
```

命令只输出会话 ID 和恢复后的消息数量，不打印正文内容。恢复后重新启动应用并检查目标会话。若 SQLite 自身报告数据库页损坏，或当前正文与上一版都不可解析，此命令无法修复；保留文件组并从独立备份恢复。

## 导出旧格式快照

切回旧版应用前，先停止所有写入进程，然后导出包含当前最新摘要与正文的 V1 JSON 快照：

```sh
pnpm run export:thread-store-rollback -- "<USER_DATA_DIR>" "<USER_DATA_DIR>/taskweaver-threads.rollback.json"
```

输出文件使用独占创建；如果目标已存在，命令会拒绝覆盖。确认导出内容和会话数量后，先把遗留的 `taskweaver-threads.json` 改名留存，再将导出文件复制到旧版应用读取的 `taskweaver-threads.json` 路径。旧版运行期间不要同时启动新版，避免两种存储各自接受写入。

新版恢复使用 SQLite 时，保留 SQLite 文件组不动。新版会在 SQLite 已初始化时跳过遗留 JSON；只有数据库不存在或尚未初始化时才会导入旧格式文件。不要通过删除 SQLite 文件来回退，也不要只切换一个文件名而忽略迁移后产生的新会话。

## 验收边界

迁移和恢复测试使用临时合成数据，未对真实用户数据目录执行迁移。自动回归覆盖旧 V1/V2 文件布局、SQLite v1 升级、并发首次启动、事务失败回滚、重试、正文损坏隔离、显式恢复、fork/delete、完整导出和真实双进程并发追加。

存储性能数据见 [`thread-store-2026-10-30.json`](benchmark-results/thread-store-2026-10-30.json)。在 Node.js v22.23.1 的 Apple M4 Pro 上，旧版整份 JSON 更新在 1/10/50 MiB 合成归档输入的 p50 分别为 3.90/34.09/172.66 ms；SQLite 只触碰小目标会话的 p50 分别为 0.139/0.117/0.108 ms。结果仅代表该设备与合成数据；逐行触碰范围由独立确定性回归验证。当前运行时 Node 暴露 `node:sqlite` experimental warning，代码未屏蔽该警告。
