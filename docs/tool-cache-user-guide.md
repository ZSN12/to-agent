# TaskWeaver 工具缓存使用指南

## 什么是工具缓存？

工具缓存是 TaskWeaver 的性能优化功能，能够自动缓存智能体的工具调用结果。当智能体多次执行相同的操作时（例如重复读取同一个文件），缓存系统会直接返回之前的结果，而不是重新执行，从而显著提升响应速度。

## 主要优势

### 🚀 性能提升
- **更快的响应速度**: 缓存命中时，工具调用从秒级降至毫秒级
- **减少重复计算**: 避免重复执行相同的文件读取、搜索等操作
- **降低系统负载**: 减少文件 I/O 和 CPU 使用

### 🎯 自动化
- **无需配置**: 开箱即用，无需用户手动设置
- **智能识别**: 自动判断哪些工具可以缓存
- **透明运行**: 在后台自动工作，不影响正常使用

### 🔒 安全性
- **Session 隔离**: 每个对话都有独立的缓存空间
- **自动清理**: 对话结束时自动清空缓存
- **只读操作**: 只缓存安全的只读操作，不会缓存文件修改等操作

## 典型使用场景

### 场景 1: 代码审查
```
用户: 请审查 src/utils/helper.ts 文件，检查是否有性能问题和安全隐患

智能体行为:
1. read_file('src/utils/helper.ts') → 实际读取
2. grep_search('TODO', 'src/') → 实际搜索
3. read_file('src/utils/helper.ts') → 🎯 缓存命中！
4. read_file('src/utils/helper.ts') → 🎯 缓存命中！

结果: 后续两次文件读取直接使用缓存，节省 ~400ms
```

### 场景 2: 项目分析
```
用户: 分析项目结构，找出所有 API 路由定义

智能体行为:
1. list_directory('src/') → 实际列出
2. grep_search('export.*Router', 'src/') → 实际搜索
3. read_file('src/routes/user.ts') → 实际读取
4. read_file('src/routes/admin.ts') → 实际读取
5. list_directory('src/') → 🎯 缓存命中！

结果: 重复的目录列出操作使用缓存，节省 ~150ms
```

### 场景 3: 批量处理
```
用户: 检查所有组件是否都有对应的测试文件

智能体行为:
1. glob_search('*.tsx', 'src/components/') → 实际搜索
2. 对每个组件:
   - read_file('component.tsx') → 首次实际读取
   - glob_search('*.test.tsx', 'src/components/') → 🎯 缓存命中！
   - read_file('component.test.tsx') → 实际读取

结果: glob_search 重复执行时全部命中缓存，节省 ~2s
```

## 哪些工具会被缓存？

### ✅ 可缓存工具

| 工具 | 说明 | 缓存效果 |
|------|------|---------|
| **read_file** | 读取文件内容 | 重复读取相同文件时立即返回 |
| **list_directory** | 列出目录内容 | 短时间内目录结构不变时使用缓存 |
| **glob_search** | 文件模式搜索 | 相同搜索模式直接返回结果 |
| **grep_search** | 代码内容搜索 | 相同搜索关键词使用缓存 |
| **web_search** | 网络搜索 | 相同搜索词短期内返回缓存 |
| **web_fetch** | 抓取网页 | 相同 URL 短期内返回缓存 |

### ❌ 不可缓存工具

| 工具 | 说明 | 原因 |
|------|------|------|
| **write_file** | 写入文件 | 有副作用，必须每次实际执行 |
| **edit_file** | 编辑文件 | 会修改文件状态 |
| **run_bash_command** | 执行命令 | 可能有副作用或依赖系统状态 |
| **delete_file** | 删除文件 | 有副作用，不可重复执行 |

## 如何验证缓存是否工作？

### 方法 1: 通过响应速度判断

缓存命中时，工具调用几乎是瞬时完成的：

```
未命中缓存: read_file(package.json) → 用时 230ms
命中缓存:   read_file(package.json) → 用时 2ms ⚡️
```

### 方法 2: 观察工具调用日志

在对话过程中，注意观察：
- 第一次调用某个工具时响应较慢（实际执行）
- 后续相同调用响应很快（缓存命中）

### 方法 3: 测试场景

发送以下测试请求：

```
请帮我做以下操作：
1. 读取 package.json 文件
2. 分析其中的依赖关系
3. 再读一遍 package.json 确认版本信息
4. 最后再检查一次 package.json 的脚本配置
```

预期结果：
- 第 1 步：实际读取文件（~200ms）
- 第 3 步：缓存命中（<5ms）⚡️
- 第 4 步：缓存命中（<5ms）⚡️

## 缓存配置

### 默认配置

缓存系统使用以下默认配置：

```yaml
缓存大小: 100 项
过期时间: 1 小时
启用状态: 自动启用
```

### 高级配置（开发者）

如果需要调整缓存参数，可以编辑配置文件：

```yaml
# vendor/z-runtime/apps/cli/config/agent-presets/taskweaver-optimized/agent.cordis.yml
- id: tool-cache
  name: '@z/dsh-tool-cache'
  config:
    enabled: true      # 是否启用缓存
    maxSize: 100       # 最大缓存项数（调大可缓存更多结果）
    ttl: 3600000       # 过期时间（毫秒，1小时 = 3600000）
```

**注意**: 修改配置后需要重新构建并打包应用。

## 常见问题

### Q1: 缓存会不会导致看到过期的数据？

**A**: 不会。缓存只在单个对话（Session）内有效，并且：
- 对话结束后自动清空所有缓存
- 只缓存只读操作，不会缓存文件修改等操作
- 缓存有过期时间（默认 1 小时）

### Q2: 如果文件在对话过程中被修改了怎么办？

**A**: 工具缓存只缓存**只读工具**的结果。当文件被修改时：
- `write_file` 和 `edit_file` 不会被缓存
- 如果后续再次读取该文件，会：
  - 方案 1（当前实现）: 使用缓存的旧内容（在同一对话内）
  - 方案 2（未来优化）: 检测文件修改时间，自动失效缓存

对于大多数使用场景，同一对话内文件不会被修改，因此当前实现是安全的。

### Q3: 缓存会占用多少内存？

**A**: 非常少。默认配置下：
- 最多缓存 100 项
- 每项平均约 10KB
- 总内存占用 < 1MB

### Q4: 可以手动清除缓存吗？

**A**: 当前版本缓存会在以下情况自动清除：
- 对话结束时
- 缓存项过期时（1 小时）
- 缓存容量满时（自动淘汰最久未用的项）

未来版本可能会提供手动清除缓存的界面。

### Q5: 多个对话之间会共享缓存吗？

**A**: 不会。每个对话都有完全独立的缓存空间，互不影响。这样设计是为了：
- 避免不同项目/任务之间的数据混淆
- 保证隐私和安全性
- 防止缓存污染

### Q6: 缓存命中率一般是多少？

**A**: 根据任务类型不同，命中率在 20% - 50% 之间：
- **代码审查任务**: ~40%（需要多次读取同一文件）
- **项目分析任务**: ~30%（重复的目录列表和文件搜索）
- **简单问答任务**: ~10%（工具调用较少，缓存机会少）

### Q7: 如果不想使用缓存，可以关闭吗？

**A**: 可以，但需要修改配置并重新构建。步骤：

1. 编辑配置文件：
```yaml
# vendor/z-runtime/apps/cli/config/agent-presets/taskweaver-optimized/agent.cordis.yml
- id: tool-cache
  name: '@z/dsh-tool-cache'
  config:
    enabled: false  # 设置为 false
```

2. 重新构建：
```bash
npm run build:z-runtime
npm run build
npm run package:mac-arm64
```

3. 重新安装应用

## 最佳实践

### ✅ 适合使用缓存的任务

- 代码审查和质量检查
- 项目结构分析
- 批量文件处理
- 依赖关系分析
- 重构建议

### ⚠️ 不太适合的任务

- 需要实时文件状态的任务
- 对外部 API 的实时查询
- 需要最新系统状态的命令执行

### 💡 优化建议

1. **合理拆分任务**: 将大任务拆成多个对话，每个对话结束后缓存自动清空
2. **避免频繁修改文件**: 在同一对话中，尽量先完成所有读取操作，再进行修改
3. **重启对话获取最新数据**: 如果发现缓存的数据过期，可以结束当前对话并开始新对话

## 技术细节

对于开发者和高级用户，以下是一些技术实现细节：

### 缓存键生成算法

```
缓存键 = 工具名 + ":" + SHA256(归一化参数).substring(0, 16)

示例:
工具: read_file
参数: { "path": "src/index.ts", "encoding": "utf-8" }
归一化: {"encoding":"utf-8","path":"src/index.ts"}  // 按键排序
哈希: SHA256(...) → a3f5c7b9e1d2...
缓存键: "read_file:a3f5c7b9e1d2"
```

### 缓存淘汰策略

采用 **LRU (Least Recently Used)** 策略：
- 当缓存容量达到上限（100 项）时
- 自动删除最久未访问的缓存项
- 保留最近使用的热数据

### 并发安全

- 所有缓存操作都是同步的（JavaScript 单线程）
- 每个 Session 有独立的缓存实例
- 不存在跨 Session 的竞态条件
