# TaskWeaver Bot 模式自动协作优化方案

> 用途：作为交给 Gemini 的产品与实现说明。目标是让用户只需描述任务，系统依据已保存的 Bot 职责自动分工；用户不必每轮重新分配角色或逐个 `@Bot`。

## 一、目标与核心决定

Bot 聊天要同时支持两种不同事情：几个 Bot 一起讨论，以及多个 Bot 分工完成一个任务。它们不应继续被混成一种“接力发言”。

核心体验：**Bot 职责在配置时设定一次；每轮用户只交代目标；系统在本轮已加入的 Bot 中自动选人、排步骤、传递交付物，并汇报进度。**调度由应用负责，不依赖 A 在回复里点名 B。

用户仍可在少数必要情况介入：职责冲突、缺少能执行的 Bot、目标存在重要歧义、或 Host 权限不允许继续时，系统清楚说明阻塞原因。正常任务不要求用户逐轮担任调度员。

## 二、当前实现基线

当前代码已经有可复用的基础，不是从零开始：

- Bot 资料保存名称、职责简介、绑定模型、工作方式和表达风格；类型定义见 `src/shared/app-api.ts`，编辑界面在 `src/features/roles/RoleModeControls.tsx`。
- 每个 Bot 在一个会话中有自己的持久 Agent session；多 Bot 共享当前工作区上下文。
- `relay` 会按传入角色顺序串行运行，并把已完成 Bot 的回复传给下一个；`independent` 会并行调用且隔离本轮回复。
- 可选汇总会在结束时再次调用主 Bot；执行中的纠偏可以发给当前 Bot 和后续 Bot。

当前缺口是：Bot 资料还没有可供调度器稳定使用的结构化职责；接力提示让后续 Bot“补充、修正或指出分歧”，没有规定实施阶段必须落实计划；没有阶段级状态、正式交接内容、审查返工和恢复机制。相关入口集中在 `backend/role-chat-service.mjs`。因此现在更像“多 Bot 轮流回答”，还不是可靠的任务流水线。

## 三、产品行为

### 3.1 讨论与自动协作

- 保留“独立回答”和“接力讨论”，用于观点比较、方案讨论和问答；不要破坏其现有语义。
- 为任务型工作增加“自动协作”语义。Bot 模式默认根据用户意图判断走讨论/回答，还是进入实施流程；用户也可以显式切换，作为清晰的覆盖选项。
- 每个会话维护已加入的 Bot 名册。用户可在会话开始时选定协作成员；**选成员不等于逐轮分配职责**。未加入本轮的 Bot 默认不应被调用，避免意外消耗额度或触碰工作区。可另设可选的“自动组队”偏好。
- 同一会话后续任务继续使用已保存的 Bot 职责。纯讨论、分析任务不应因为加入了实施型 Bot 就自动改代码。
- 用户在消息中明确点名或覆盖职责时，尊重本轮明确指令；否则采用已保存职责。

### 3.2 自动识别任务类型

把每条用户消息分为足够少、可解释的路由类型：

| 路由类型 | 典型意图 | 默认行为 |
| --- | --- | --- |
| `answer` | 问答、比较、解释 | 让匹配的 Bot 回答；可按讨论设置独立或接力 |
| `investigate` | 检查、诊断、找问题、提出建议 | 由研究/规划型 Bot 读取并报告，保持只读 |
| `execute` | 修复、实现、优化代码或完成有明确产物的工作 | 自动规划（按复杂度）、实施、审查 |

路由器应结合用户目标、会话上下文和已选 Bot 职责，而不是只匹配“修复”等关键词。优先采用确定、可测试的规则；边界不清时才使用受约束的意图判定。若不能确认用户授权了写入行为，不得默默进入写入阶段，应先做只读分析或询问一次。

## 四、Bot 职责配置与自动分工

不要要求用户每轮再选“谁规划、谁实施、谁审查”。在 Bot 管理中复用现有的名称、职责简介和工作方式，自动归纳并保存一个结构化职责标签，供调度器使用：

- `planner`：拆解目标、检查风险、给出实施方案和验收条件。
- `implementer`：编辑工作区、运行验证、汇报实际改动。
- `reviewer`：对照目标和改动审查缺陷、遗漏及回归风险。
- `researcher`：检索、阅读和汇总证据。
- `specialist`：在指定专业领域提供判断或执行专长任务。
- `generalist`：未明确专长的通用助手。

要求：

1. 保存资料时自动从现有描述推断职责，不要求用户重新填写一套冗余配置。可在编辑器中显示推断出的职责标签，并允许用户一次性纠正。
2. 现有 Bot 资料无须重建；迁移采用向后兼容的默认值。未标注资料应从已有职责简介和工作方式推断，不能推断时使用 `generalist`，并在界面标明。
3. 可以支持一个主要职责和若干能力标签。多个 Bot 匹配同一阶段时，按明确优先级和稳定规则选择；不依赖模型名字，也不依赖 Bot 在顶栏的视觉顺序。
4. 规划/实施/审查是工作职责，不等于 Host 权限。角色描述不能扩大实际工具权限。

## 五、自动协作流程

### 5.1 标准路径

对需要实施的任务，按以下阶段自动运行；缺少某类 Bot 时跳过该阶段并明确说明，不伪造已完成的工作。

1. **规划**（复杂任务或用户要求方案时）：规划 Bot 读取相关代码，交付目标理解、步骤、涉及范围、验收标准、风险和待确认点。不得修改文件。
2. **实施**：实施 Bot 自动接收原始请求、规划结果、验收条件、用户纠偏和当前工作区信息；按当前 Host 授权实施并验证。无需用户再 `@` 它。
3. **审查**：审查 Bot 接收原始请求、规划结果、实施报告、验证结果和本轮实际改动；检查是否满足验收条件，并给出带严重程度与文件位置的问题。
4. **有限返工**：发现必须修复的问题时，把审查发现交给实施 Bot，再由审查 Bot复核；默认最多两轮。超限后停止并报告，不能无限循环。
5. **汇总**：合并计划、实际改动、测试结果、审查结论和未解决风险，说明哪些已完成、哪些受阻。

简单任务可跳过规划；纯解释/讨论任务不启动实施或审查。只有一个实施 Bot 时可直接执行，并在需要时由另一个已加入的 Bot 审查。审查者缺席时应显示“本轮未配置审查 Bot”，不能把实施 Bot 自检称为独立审查。

### 5.2 阶段交接数据

阶段交接不只依靠长文本聊天记录。为每个阶段保存经过校验的交付内容，至少包括：

- 原始用户目标和本轮补充/纠偏。
- 规划结果：目标、步骤、验收条件、风险、待确认问题。
- 实施结果：实际改动文件、执行过的验证及结果、未完成事项。
- 审查结果：问题列表（严重程度、文件与位置、理由）、通过/未通过结论。
- 阶段状态、Bot ID、开始/结束时间、错误类别和可恢复信息。

给下游 Bot 的上下文应明确区分“用户要求”“上游方案”“实际验证证据”和“尚未证实的判断”。失败的上游阶段不能被下游当作成功结果继续执行。

### 5.3 A/B/C 示例

用户已保存 A=规划、B=代码实施、C=审查，并把三者加入当前会话。用户只发送“修复这个会话追加消息后界面空白的问题”。系统应自动：

1. 让 A 检查并给出复现路径、修复计划和验收条件。
2. 将 A 的计划交给 B；B 修改代码并运行相关测试。
3. 将本轮改动和测试证据交给 C；C 检查改动是否解决原问题、有无回归。
4. 如 C 找到必须修复的问题，自动限次退回 B；最后呈现结果。

用户不用在消息里重复写“@B 去实现、@C 去审查”。如果用户说的是“分析为什么出现这个问题，不要改代码”，则只做只读诊断，不启动实施阶段。

## 六、权限、共享工作区与安全

- 所有阶段继续通过现有 Host 权限和沙箱执行。有效能力应是“用户当前授权”与“本阶段所需能力”的交集；不得绕过审批、沙箱或文件边界。
- 规划阶段只读；实施阶段只有在 Host 当前权限允许时才能写入；审查阶段必须以 Host 强制的只读限制运行。不能仅靠 Persona 写“只读”就宣称权限已隔离。
- 如果现有权限服务不支持阶段级只读，需要先扩展权限执行上下文并补边界测试；在此之前应阻止审查 Bot 调用写入能力，不能把 UI 标签当作沙箱边界。
- 所有 Bot 使用同一工作区时，审查范围必须只包括本任务产生的改动。实施开始前记录工作区基线，审查时用可验证的本轮改动证据区分用户已有的未提交修改；不得自动重置、覆盖或回滚用户原有改动。
- 同一工作区内的写入型任务应避免互相覆盖；可以排队或提示冲突，但创建新会话和只读查询不应被全局锁住。
- 不在阶段交接、日志或错误信息中暴露凭据、密钥和不必要的环境变量。

## 七、任务状态、纠偏与恢复

每个任务应有持久状态：`queued`、`planning`、`awaiting_approval`（仅当用户启用了计划确认）、`implementing`、`reviewing`、`revising`、`completed`、`blocked`、`failed`、`cancelled`。

- 默认可设置为计划完成后自动继续；计划确认是用户可保存的偏好，不是每轮必经步骤。
- 任务中纠偏发送给当前运行阶段，并写入后续阶段输入。如果纠偏实质改变目标或范围，应使旧计划失效并重新规划，而非把过期计划继续交给实施者。
- 每阶段单独记录结果。应用重启后可从最后一个未完成阶段恢复，不重跑已完成阶段、不丢失之前 Bot 输出。
- 重试有上限并按失败类型区分；权限拒绝、用户取消、模型错误、验证失败均要显示真实状态，不得伪报成功。
- 每个 Bot 保留自己的会话记忆；任务阶段交接是额外、明确的上下文，不应把不同 Bot 的私有 session 混成一个 session。

## 八、界面要求

- Bot 管理页继续让用户用自然语言填写职责；自动识别的职责标签可查看、可一次性调整，不要求每轮设置。
- 当前会话记住加入的 Bot 名册。成员选择只决定本会话可用团队，不决定每轮工作职责。
- Bot 模式提供清楚的“自动协作 / 讨论”入口。自动协作由系统按用户意图决定阶段；讨论模式保留独立/接力选项。
- 自动协作时显示阶段时间线和当前执行者，例如“规划完成 → B 正在实施 → 等待 C 审查”，每阶段可展开阅读交付内容、文件改动、验证结果和审查意见。
- 显示“为什么选这个 Bot”和缺失职责提示，提升可解释性；允许用户纠偏、暂停、取消、重试当前阶段。
- 默认避免每阶段都要求用户确认；提供“计划完成后暂停，等我确认”的持久偏好。

## 九、建议实现顺序

1. **先固定语义与数据模型**：增加职责标签、自动识别来源、任务意图和阶段状态类型；兼容现有 Bot 配置及历史会话。
2. **实现路由决策**：输入用户目标、会话成员和已保存职责，输出可解释的阶段列表及参与者；覆盖回答、只读诊断、实施三类任务。
3. **实现后端阶段调度与交接**：串行启动必要阶段，保存结构化结果，处理纠偏、取消、失败、限次返工和重启恢复。
4. **落实权限与改动归属**：阶段级能力与 Host 授权求交集；建立本轮改动证据，确保审查不会把已有未提交修改误认成本轮产物。
5. **实现 UI 时间线与偏好**：资料职责标签、自动协作状态、阶段结果、可选计划确认、缺失职责与恢复状态。
6. **回归与灰度验证**：先用模拟 Bot 测序列和错误状态，再用隔离测试工作区进行一次真实端到端任务；通过后再作为默认 Bot 行为逐步启用。

若需增加 IPC 能力，`contract/channels.mjs` 是唯一契约来源；按仓库规范生成 Shell bridge 和 IPC 类型并运行契约检查。不要从 Renderer 直接访问 Node。

## 十、验收标准

1. A/B/C 已保存各自职责并加入会话后，用户只发一个实施任务，不写 `@`，系统能自动按职责规划、实施、审查。
2. B 收到 A 的正式计划及验收条件；C 能看到 B 本轮实际改动和验证结果，而不只看到 B 的口头总结。
3. 用户只要求解释、诊断或讨论时，不触发写入阶段；没有实施型 Bot 时不假装任务已完成。
4. 任务参与者由职责和任务相关性决定，不依赖 Bot 名称、模型名或顶栏顺序；未加入的 Bot 不会被意外调用。
5. 审查者的只读限制由 Host 权限强制；模拟尝试写入必须被拒绝并有测试证明。
6. 审查失败最多触发设定次数的实施返工，完成或受阻状态、阶段输出和错误都能在 UI 中查看。
7. 任务纠偏会到达正确的当前/后续阶段；修改目标后旧计划会失效并重新规划。
8. 关闭或重启应用后可以恢复未完成阶段；不会重复执行已完成阶段，也不会清除用户原有未提交改动。
9. 现有独立回答、接力讨论、Bot 角色配置、会话历史和权限行为回归通过。

## 给 Gemini 的实施要求

请先阅读仓库 `AGENTS.md`，再检查 `git status` 和现有角色模式代码。工作区已有大量与本任务无关的用户修改，必须保留；不要 `reset`、`clean`、覆盖或顺手重写无关文件。优先按以上阶段交付可审查实现；改动 IPC、持久化、权限、文件差异或恢复逻辑时增加失败与边界测试。遵守现有 Host 权限和沙箱，不得把角色人设或界面设置当作权限边界。最终说明实现范围、运行过的检查、未完成事项和仍需验证的风险；没有完成的阶段不要声称已完成。
