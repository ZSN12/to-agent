### OPT-2026-10-07-09 — 显式工作区上下文预算实测（暂不定最优值）

- **问题：**计划中的 16 KiB 是候选上限，没有真实质量/时延数据支撑，不能直接当作最优值。
- **隔离上下文实验：**真实毕设仓库 `@dir:electron/backend`；同一条只读权限/沙箱问题、MiMo-V2.6-Flash、Medium、`taskweaver-readonly`、隔离 Z Host；禁止工具调用以单独比较预加载材料。成功轮次均为 1 个模型 step、0 次工具调用。
- **隔离实验结果：**

  | 上限 | Host 注入字节 | 输入 / 输出 tokens | 首段文字 | 总耗时 | 观察 |
  |---:|---:|---:|---:|---:|---|
  | 16 KiB | 16,384 | 6,872 / 3,108 | 39.9 秒 | 回答覆盖权限映射与部分沙箱边界；没有带入权限服务/线程持久化证据，模型说明证据不足。 |
  | 32 KiB | 32,768 | 10,560 / 7,868 | 105.4 秒 | 回答增加权限服务细节，但仍缺少完整线程状态持久化证据。 |
  | 48 KiB | 49,152 | — | — | 模型服务返回 `content_filter`，该样本失败，不计入质量/时延比较。 |
  | 64 KiB | 65,536 | 18,388 / 8,152 | 64.6 秒 | 本组回答覆盖最完整，涉及权限服务、线程状态、沙箱覆盖及审计；输出也明显更长。 |

- **Agent 实用实验：**同仓库、同模型/推理档/只读预设、同一只读任务，允许 Agent 用只读工具补充缺失文件；仅改变预注入上限。

  | 上限 | 预载文件数 | Host 输入 / 输出 tokens | 模型 steps | 工具调用（grep/read/glob） | 首段文字 | 总耗时 |
  |---:|---:|---:|---:|---:|---:|---:|
  | 16 KiB | 4 | 45,648 / 14,214 | 31 | 49（29/18/2） | 396.6 秒 | 414.8 秒 |
  | 64 KiB | 10 | 53,141 / 16,171 | 29 | 48（32/14/2） | 369.8 秒 | 397.0 秒 |

- **Agent 实用实验结论：**64 KiB 多注入了文件，答案更完整；总时延仅少约 18 秒（约 4%），工具调用只少 1 次，却多消耗 9,450 个 Host 统计 tokens（约 16%）。16 KiB 轮次仍花近 7 分钟才开始回答，说明主要瓶颈还包括 Agent 的跨层检索/推理收敛，而不只是初始上下文量。
- **注意：**这组 Agent 轮次的工具数和模型 steps 与隔离实验不同；不可把隔离实验的“单步时延”当作真实 Agent 端到端时延。真实 Agent 任务中，16 KiB 与 64 KiB 都进行了约 48–49 次检索/读取，差异很小。
- **结论边界：**每档只有一次有效调用，模型服务存在时延与回答长度波动，不能据此认定精确最优值，也不能推断所有任务会有相同的质量/速度权衡。48 KiB 的拒绝样本不纳入比较。
- **额外发现：**`electron/backend/dsh-chat-service.mjs` 约 81,064 字节，现有单文件 32 KiB 上限会使其不进入 `@dir:electron/backend` 预载；单纯提高总预算仍无法覆盖这个核心文件。后续应优先研究按相关性分块/按需读取，而不是只放大全局上限。
- **决策：**生产默认暂留 16 KiB，明确标记为**临时防护上限而非已验证最优值**；不因单次 A/B 直接提高到 64 KiB。优先改善按需检索和大文件分块，再以多轮配对数据决定预算。真实 smoke 脚本新增 `--context-budget` 用于复测候选值；普通生产调用不传该参数，行为不变。
- **验证：**`npm run test:workspace-context`、`npm run test:backend`、`npm run build` 通过；真实模型报告保存在本机临时目录。隔离 smoke 会临时以权限 `0600` 复制运行所需的 DSH 凭据/设置文件，不显示其内容；正常完成后在 `finally` 中删除副本。

### OPT-2026-10-07-09A — 上下文预算三档真实 Agent 复测

- **目的：**验证 16 KiB 是否过小，并观察 32/64 KiB 是否能减少 Agent 补读；不把注入上限误当成模型总上下文窗口或任务总预算。
- **控制条件：**同一毕设工作区、同一只读任务文本、`xiaomi/mimo-v2.6-flash`、`taskweaver-readonly`、隔离本地 Z Host；只改变 `assembleWorkspaceContext` 的候选上限。没有写入、shell 或构建/测试操作。三次都使用真实模型请求，结果保存在本机临时目录。
- **本轮结果（每档单样本）：**

  | 注入上限 | 实际注入 | 首段文字 | 总耗时 | 模型 steps | 只读工具调用 | 观察 |
  |---:|---:|---:|---:|---:|---:|---|
  | 16 KiB | 16,353 B | 63.8 秒 | 116.3 秒 | 8 | 13 次调用；仍需补查权限映射、沙箱、IPC 和 Host 路径，若干环节因证据不足标为未核实。 |
  | 32 KiB | 32,742 B | 52.8 秒 | 65.9 秒 | 6 | 10 次调用；链路覆盖较完整，是本组最快样本，但权限服务细节仍有未核实项。 |
  | 64 KiB | 65,536 B | 101.3 秒 | 112.4 秒 | 7 | 12 次调用；答案细节略多，但比 32 KiB 慢，且首段文字最晚。 |

- **相关性检查：**对同一条任务提示单独重放生产 `sandboxContextLine`，沙箱说明占 309 B；16/32/64 KiB 下文件集合分别为 4/6/10 个，64 KiB 才带入 `permission-service.mjs` 与 `dsh-permission-map.mjs`。注意：本次真实 smoke 直接调用 `dsh-chat-service`，没有经过 `register-ipc`，所以实跑表中的注入字节未包含这 309 B；重放证明加入后仍不会改变文件集合。16 KiB 实际预载 `task-profile.mjs`、`user-intent.mjs`、`app-preferences.mjs`、`dsh-session-model.mjs`，没有权限服务/权限映射；32 KiB 也没有这两个核心文件。由此看，当前排序/截断策略是重要混杂因素：增加预算能碰巧带入更多相关源码，但并非稳定的检索替代。
- **结论边界：**32 KiB 在本次窄任务样本中表现最好；单次运行且模型输出/服务延迟有波动，不能据此证明 32 KiB 普遍更优。此前宽范围真实任务的一对样本是 16 KiB 414.8 秒、64 KiB 397.0 秒，差约 4%，却多约 9,450 个 Host 统计 tokens；不同任务不可合并计算成稳定均值。现有证据**不支持把 16 KiB 宣称为最优值，也不足以直接将生产默认改成 32/64 KiB**。
- **当前决策：**生产仍暂留 16 KiB 作为注入防护上限；下一步优先修复按任务相关性选文件、显式展示截断/注入量，再用同一任务做至少 3 组交错顺序的重复对照后决定默认值。该上限只限制本轮显式工作区注入，不限制模型原生上下文窗口，也不是任务预算。
- **报告：**16 KiB `/var/folders/y2/8tky9bh97pn991dp9g6gv1_00000gn/T/taskweaver-live-read-zTw3EK/report.json`；32 KiB `.../taskweaver-live-read-2hGuJN/report.json`；64 KiB `.../taskweaver-live-read-1qgkzg/report.json`。
- **发布状态：**本轮只追加实测记录，没有修改生产预算或安装应用。

### OPT-2026-10-07-09B — 同提示三档上下文预算真实 Agent 对照

- **目的：**回应 16 KiB 缺乏依据的问题，在真实模型 Agent 上同题比较 16/32/64 KiB，而非只用上下文组装单测推断。
- **控制条件：**毕设工作区、相同 `@dir:electron/backend` 引用与同一权限审批链路核查提示、`xiaomi/mimo-v2.6-flash`、Medium、`taskweaver-readonly`、每轮独立隔离 Z Host；唯一主动改变项是工作区上下文注入上限。所有有效轮次均完成；未修改文件，未运行 shell/测试/构建。每档仅 1 次。
- **实测：**

  | 注入上限 | 实际注入 | 首段文字 | 总耗时 | 模型 steps | 工具调用 | 回答覆盖 |
  |---:|---:|---:|---:|---:|---:|---|
  | 16 KiB | 16,384 B | 83.6 秒 | 109.1 秒 | 10 | 覆盖 UI/IPC、本地与 Host 审批路由、action 校验和失败时保留审批框；个别挂载位置只 grep 定位。 |
  | 32 KiB | 32,768 B | 134.0 秒 | 155.0 秒 | 12 | 四项均回答，补充读取 App/preload/权限服务；较 16 KiB 更完整，但未更快。 |
  | 64 KiB | 65,536 B | 54.6 秒 | 191.6 秒 | 14 | 四项均回答且源码细节最多；首段最早，但尾部继续推理更久，总耗时最长。 |
