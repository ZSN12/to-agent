## 1. 高危：未选工作区 → 会话绑定到文件系统根

### 现象

没有选择工作区就发消息时，该会话的 DSH 会话 `cwd` 会变成 `process.cwd()`。
打包版从 Finder 启动时 `process.cwd()` 是 `/`，于是会话被永久绑定在文件系统根。

### 证据链

```
register-ipc.mjs:85    const fallbackWorkspace = process.cwd()
register-ipc.mjs:207   const workspacePath = state.workspacePath || fallbackWorkspace
register-ipc.mjs:1137  chat.send({ cwdOverride: runtimeContext.workspacePath, ... })
dsh-chat-service.mjs   ensureSession → api.sessions.create({ cwd: requestedCwd })
```

本机落地结果：

```
dsh/sessions/--root--/tw-39b768f0-0a18-4183-a0f2-186d3ae493ff/session.jsonl.zstd   30 KB
taskweaver/dsh-session-map.json  →  39b768f0-… : { "cwd": "/" }
taskweaver-threads.json          →  39b768f0-… : { "workspacePath": null, messages: 14 }
```

### 为什么这是安全边界问题

DSH 的沙箱边界就是**会话 cwd**（`dsh-source/packages/sandbox/sandbox-policy/lib/index.js:138`）：

```js
resolve(request = {}) {
  return {
    mode: request.mode ?? ... ?? this.defaultMode,
    workspaceRoot: resolveWorkspaceRoot(session?.header.cwd ?? this.workspaceRoot),
    ...
  }
}
```

注释原文：*"A session cwd is its workspace-write boundary"*。

所以当 `cwd = /` 时：

- `workspace-write` 模式的允许范围 = 整个文件系统，**"只能写工作区内" 这条约束完全失效**；
- 会话内的 bash / 文件工具都以 `/` 为默认工作目录；
- `@file:` / `@dir:` 引用的 `isWorkspacePath(root, target)` 检查退化为恒真（任何路径都在 `/` 之下）。

### 为什么它不可逆

`app-state-store.mjs:114 setWorkspace()` 只在**当前线程没有消息**时才原地改工作区，
否则新建线程。所以已经聊过的会话，其 `workspacePath: null` 会一直保留 → `cwd` 永远是 `/`。

### 建议修法（三选一，按侵入度递增）

1. **最小**：在 `ensureSession` 里拒绝把会话建在文件系统根上，抛明确错误
   （「当前对话未绑定工作区，请先选择工作区」），而不是静默建在 `/`。
2. **推荐**：在 `getConversationRuntimeContext` 里区分「用户没选工作区」和「工作区是 `/`」，
   没选时直接阻断发送并给出可操作提示。
3. **彻底**：`fallbackWorkspace` 不再用 `process.cwd()`，改为在启动时校验
   `process.cwd()` 是否是一个真实工作区，否则视为未设置。

## 2. 中危：删除对话不回收 DSH 侧

### 现象

`dsh-chat-service.mjs` 的 `resetSession` 是**空实现**：

```js
// Switching conversations/workspaces must not destroy DSH's durable history.
resetSession: async () => {},
```

`app:deleteThread` 只调用它，然后删 UI 线程：

```js
if (before.currentThreadId === threadId) await chat.resetSession()   // ← no-op
const state = await appState.deleteThread(threadId)
```

### 后果

1. **孤儿映射**：映射表条目永不删除 → 每次启动 `loadSessions()` 都会把它们加载进内存。
2. **孤儿日志**：`dsh/sessions/<slug>/<sessionId>/session.jsonl.zstd` 保留完整会话内容
   （含用户 prompt 全文），磁盘上永久可读。本机实测残留 63.5 KB。
3. **不可搜索性不一致**：UI 里删掉的对话，其内容仍以明文会话日志形式存在。

### 建议修法

新增 `forgetConversation(conversationId)`：从 `sessions` 移除 + 重新持久化 + 断开 hub attachment；
由 `app:deleteThread` / `app:clearConversation` 调用。**是否同时删除 DSH 会话目录需要你拍板**
（那是破坏性操作，删了就找不回历史）。

## 3. 中危：会话映射表无上限增长，编排会放大

`ensureSession()` 对每个新 `sessionKey` 都会 `sessions.set(...)` + `persistSessions()`，
且没有任何回收路径。

编排路径给每个子会话都生成独立 key（`orchestration-service.mjs`）：

```
tw-orchestration-<conversationId>-<runId>-planner
tw-orchestration-<conversationId>-<runId>-planner-retry
tw-orchestration-<conversationId>-<runId>-<taskId>     ← 每个子任务一条
tw-orchestration-<conversationId>-<runId>-synthesis
```

一次 8 子任务的编排 = 往映射表里永久写入 **11 条**，并在磁盘上建 11 个 DSH 会话目录。
本机目前没有编排记录（`编排/任务类条目: 0`），属**潜在**问题。

> 顺带：`orchestration-service.mjs:529` 的 `sendTaskMessage` 回退 key
> `tw-orchestration-<conversationId>-<taskId>` **不含 runId**，若某任务的 `dshSessionKey` 缺失，
> 同会话第二次运行的同名任务会复用上一轮的 DSH 会话 → 跨轮上下文串味。建议去掉这个回退，
> 或补上 runId。

## 4. 中危：UI 有历史、模型是空的

### 机制

仓库里**没有任何对话历史注入逻辑**（legacy 注入已在之前删掉）：

- `register-ipc.mjs:1039 preparePromptByWorkMode()` 只注入意图指引，不带历史；
- `context-assembler.mjs` 只处理 `@file:` / `@dir:` 显式引用。

所以模型的上下文**完全等于 DSH 会话日志**。一旦会话日志是空的，模型就是失忆的，
而 UI 仍然显示着线程里的消息。

### 两个触发场景

1. **fork 线程**：`app:forkThread` 复制了 UI 消息，但 `resetSession()` 是 no-op，
   而 fork 会产生新的 `conversationId` → 新 DSH 会话是空的 → **fork 出来的对话没有上下文**。
2. **老对话 / 迁移对话**：本机 `ace15b09-…`（22 条消息，工作区 `/Users/zsn/Documents/毕设`）
   和 `d3bdf245-…`（6 条消息）都不在映射表里、也没有 DSH 会话目录。
   一旦给它们发消息，`ensureSession` 会新建一个空会话 → 模型从零开始。

### 建议修法

- fork 时把 DSH 会话也 fork（DSH 有 `sessions.fork`），或至少在 UI 上明确提示"新分支不继承上下文"；
- 对「有消息但无 DSH 会话」的线程，首次发送时给出一次性提示，或把 UI 历史压缩成一段摘要注入（注意别做成每轮重发）。

## 6. 已验证「没问题」的部分（不用担心）

这些我逐条查过，隔离设计是对的：

1. **DSH 沙箱按会话 cwd 划界**，不是全局变量 —— `sandbox-policy.resolve()` 用 `session.header.cwd`。
2. **权限判定用 `AsyncLocalStorage`** —— `permission-service.mjs:19 activeExecution = new AsyncLocalStorage()`，
   并发会话各自的 mode / webContents / conversationId 互不串。
3. **渲染层按 conversationId 过滤** —— `useDshConversationView.ts:32` 过滤 `chat:dshView`；
   `useAppBackend.ts:305` 过滤 `chat:stream`；并且为每个会话单独维护
   流式缓冲（`conversationStreamRef`）、运行集合（`runningConversationsRef`）、
   权限提示（`permissionPromptsRef`）、编排选择（`orchestrationChoicesRef`）。
   切走再切回会通过 `applyConversationStreamSnapshot` 恢复现场。
4. **中止按会话** —— `chat:stop` → `resolveIpcConversationId` → `chat.abort(conversationId)`
   + `orchestration.abort(conversationId)`，不会误杀别的会话。
5. **编排子会话 id 不撞车** —— sessionKey 带 `conversationId` + `runId`。
6. **发送互斥按会话** —— `withTurnLock(conversationId)` / `assertNotBusy(conversationId)`。
7. **工作区按会话** —— `cwdOverride: runtimeContext.workspacePath`，不是全局。

### 8.2 关键设计决定

**① 用 `workspaceBound` 而不是「路径等于 `/`」判定。**
原来的 bug 是 `state.workspacePath || fallbackWorkspace` 把「没选工作区」和「工作区是某个路径」混成一件事。
现在运行上下文里带上 `workspaceBound`，发送前判它；`dsh-chat-service` 里再用 `assertBindableWorkspace` 做第二道闸（防住任何绕过 IPC 的调用方，例如编排子会话）。

**② 校验放在 `ensureReady()` 之前。**
无效请求不该把 DSH Host 拉起来，也不该产生 `/permission` 提示。

**③ `forgetConversation` 只删映射，不删日志。**
同时回收 `ownerConversationId` 指向该对话的编排子会话条目（key 形如 `tw-orchestration-<convId>-<runId>-*`）。
幂等；重复调用返回空数组。

**④ LRU 只淘汰「可推导」条目。**
主会话的 DSH 会话 id 恒为 `tw-<sessionKey>`，丢掉条目后下次 `ensureSession` 会用同一个 id
重新 attach 到磁盘日志（`sessions.create` 显式 id = attach/resume 路径），**上下文不丢**。
fork 出来的子会话 id 由 DSH 随机生成（`session-<uuid>`，见 `api-proxy.js` 的 `session.fork`），
丢掉就无法重建 —— 会让分支直接失忆，所以**永不淘汰**。正在运行的会话同样跳过。
淘汰只动映射表与内存索引，**不删磁盘日志**。

**⑤ fork 的切分点用「前 N 轮」而不是猜 seq。**
`session.fork` 的 `atSeq` 语义是「切在包含该 seq 的那个已完成 turn 的末尾」，所以第 N 个
`turn/end` 的 seq 正好表示「保留前 N 轮」。UI 侧一个 user 消息对应一个 turn，于是
`register-ipc` 用「切片里的 user 消息数」当 N，`dsh-chat-service` 再用 `sessions.history`
翻页取出真实的 `turn/end` seq 列表来换算。**轮数超过日志长度时退化为整段继承**（不带 atSeq），
而不是切在错误的轮次上；DSH 拒绝 fork（如没有已完成 turn）时不写半成品映射。

### 8.4 副作用与注意事项

- **未绑定工作区的对话现在不能发送**。这是刻意选择。用户选工作区后，若当前对话已有消息，
  `appState.setWorkspace` 会**新建一个带工作区的对话**（`app-state-store.mjs:121-126`），
  原对话保留为只读历史。
- 本机已存在的 `39b768f0-…`（`cwd=/`，14 条消息）属于这一类：打开后需重新选工作区。
- **淘汰映射条目会丢失该对话的 `cwd` 绑定记录**。下次重建时用的是「当前工作区」，
  若用户中途换过工作区，重建后的会话 cwd 与日志里的 header 可能不同。
  因为 `ensureSession` 有「cwd 不一致就拒绝」的守卫，这一情况表现为报错而不是静默错乱。
- `app:clearConversation` **没有**接入 `forgetConversation` —— 它只新建对话，
  不删除旧对话，因此旧对话的映射条目是合法的，不该被回收。

### 9.2 顺带修掉的两个真问题

1. **降级提示用户看不到**。多 Agent 规划失败降级为单 Agent 时，提示原来靠
   `chat:stream` 的 `orchestration` 事件传 → 被丢弃。现在改为挂在最终助手消息的
   `callout` 上（`createAssistantMessage` 优先用 `result.callout`）。
2. **降级后 callout 会写成「拆分并执行 0 个子任务」**。因为降级路径下 `tasks` 是空的，
   而旧逻辑只看 `execution.mode === 'multi-agent'`。现在 `result.callout` 优先，不会误报。
