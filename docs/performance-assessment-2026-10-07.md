## 2. 用户感知延迟分析

### 观察数据

来自 `docs/acceptance-2026-10-06.md` 的九轮真实调用：

| 指标 | 中位数 | 范围 |
|---|---:|---|
| 首次 Think | 4.6s | 2.7-8.3s |
| 首次正文 | **102.9s** | 51.9-173.0s |
| Steps | 11 | 8-17 |

### 延迟构成

**从用户提交到首次正文的 ~103 秒里：**

1. **0-5 秒**：首次 Think 出现（✅ 快）
2. **5-103 秒**：模型执行多轮工具调用
   - 多次 `grep` / `find` 搜索
   - 多次 `read` 读取文件
   - 每次工具后需要模型决策下一步
3. **103 秒后**：开始输出正文

### 关键结论

**文档原话**：
> "用户看到 Think 后长时间无正文的主要观察区间发生在多轮工具/模型步骤中，不能单归因于工作区注入字节数。"

**这不是技术瓶颈，是模型推理策略**：
- 模型选择先搜索、多次读取、充分理解代码后再回答
- 这是**正确的行为**（深度理解 > 快速猜测）
- 优化方向是 prompt engineering 和模型选择，不是代码重构

## 3. 工具执行反馈完整性

### 已实现功能

✅ **实时工具状态显示**（`DshToolCallList.tsx`）：
- 运行中工具的名称和摘要
- 实时状态点（ongoing/done/error/warning）
- 批量工具调用折叠/展开
- 每个工具的耗时（毫秒/秒）
- 失败计数统计

✅ **流式输出**（`dsh-chat-service.mjs`）：
- 接收 `assistant/chunk` 事件
- 转发 `text-delta` 到前端
- 前端正确累积 `streamText`

✅ **Think 状态**：
- `thinking_start` / `thinking_delta` / `thinking_end`
- 显示推理时长
- 工具执行时暂停 Think 计时

### 用户体验流程

用户提交问题后看到的完整时序：

```
[0-5s]    Think 开始...
[5-20s]   工具调用: grep · 搜索相关文件 · 正在执行
[20-30s]  工具调用: read · package.json · 正在执行
[30-50s]  Think 继续...
[50-70s]  工具调用: read · src/main.ts · 正在执行
[70-103s] Think 继续...
[103s+]   开始输出正文...（流式）
```

**所有环节都有实时反馈**，用户不会看到"卡死"状态。

## 5. 优化建议

### ✅ P0（已完成）

1. **服务层性能验证** — 已证明无开销
2. **工具执行反馈** — 已完整实现

### 🎯 P1（真正的优化方向）

#### 1. 减少模型多轮工具调用（非技术瓶颈）

**当前状态**：
- 单任务 8-17 steps
- DAG 子任务最多 31 次工具调用

**优化方向**：
- 改进 system prompt（引导模型更高效搜索）
- 调整 Agent preset（减少过度搜索）
- 提供更好的上下文（预载关键文件）
- 换用推理更高效的模型

**预期收益**：
- 首次正文从 ~103 秒降到 ~30-50 秒
- 总 steps 从 11 降到 3-5

#### 2. 优化 DAG Planner 质量

**当前问题**：
- 子任务范围分配不够精确
- 重复搜索/读取
- 有时触发循环保护

**优化方向**：
- 改进 Planner prompt（更明确的范围边界）
- 增加工具调用去重
- 子任务间共享搜索结果缓存

**预期收益**：
- 31 次调用降到 <10 次
- 并发效率从 7.7-44.6 秒提升到 5-20 秒
