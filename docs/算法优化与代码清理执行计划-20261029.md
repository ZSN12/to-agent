## 1. 目标、范围与当前状态

本轮目标：修复已经复现的检索错误，消除主要平方级算法和并发重复工作，回收无界缓存，删除没有生产消费者的代码，并把这些约束放进可重复运行的检查。

完成后应达到：

- 带文件/语言/类型过滤的语义搜索不再因全局候选截断而漏掉范围内结果。
- Markdown、聊天工具归属和消息导航的处理量随输入近似线性增长。
- 同一代冷缓存的并发请求共享工作，不重复扫描目录或读取凭据。
- 缓存按会话、工作区和 Host 生命周期管理，有明确容量与释放规则。
- 事件窗口和变化后的全文搜索尽量只处理受影响数据；会话小更新不再被全部归档正文拖慢。
- 删除候选有调用链证据，部署入口、公开契约和用户数据保持可恢复。

2026-10-29 初始核对状态：

- **已实施、待本计划验收**：线程预览目录、四个通用工具模块、部分孤立测试、一次性脚本、wait-on 和部分过时文档的清理；这些来自已有工作区改动。
- **已接入、待核对覆盖**：根 `check:dead-code`、Knip 配置、部分性能和语义搜索测试入口。
- **仍待处理**：ESLint 的 backend/contract 覆盖、报告中的主要算法热点、Runtime 清理和存储优化。
- **未作承诺**：全量 vendor 逐行审计、移除 runtime/lib、切换技术栈、增加向量数据库、重写模型路由、真实账号调用和发布。

执行时重新读取工作区状态；发现其他改动已完成的项，核验证据后转为完成，不重复实现。

## 2. 交付顺序与依赖

建议按八个阶段交付，每阶段拆成可独立审查的小提交：

1. **P0：固定基线，补齐检查与源码验证。**
2. **P1：修复语义搜索和 Markdown 两个首要问题。**
3. **P2：合并并发冷工作，修复流解析及索引生命周期。**
4. **P3：优化聊天历史、缓存和界面派生数据。**
5. **P4：完成剩余无用实现和生成副本清理。**
6. **P5：优化事件窗口、FTS 更新与冷日志观察。**
7. **P6：优化 usage 与会话正文持久化。**
8. **P7：集成回归、性能复测和交付收口。**

主要依赖：P0 是所有阶段的前置；P4 的语义搜索清理依赖 P1，避免构造参数与过滤接口同时被两处改动；P5 的目录观察优化先于 P6 的存储迁移验收；P7 依赖其余阶段验收完成。

P1 的 Markdown 与检索可分别实施；P2 的工作区索引与 Provider 传输可分别实施。并行时必须分配互不重叠的文件所有权；同一个 semantic-search 包、同一个 MainConversation 和持久化共享结构按顺序修改。

里程碑：

- **M1：P0—P2。** 正确性问题闭合，平方扫描和并发放大有可重复证据证明改善。
- **M2：P3—P5。** 聊天缓存受控、清理收口、窗口与搜索不再无条件全量处理。
- **M3：P6—P7。** 持久化规模问题与迁移风险经过验收，产出最终性能和变更报告。

这些是交付顺序，不是已完成状态，也不是固定日历工期。存储阶段先通过设计与故障恢复验证，再进入迁移，不为赶时间跳过验收。

## 3. P0：固定基线与检查门槛

### P0.1 工作区与独立检查点

- 输入：当前 Git diff、已有未跟踪文件、暂存状态和其他会话正在修改的范围。
- 动作：记录起始提交、改动清单及责任域；批量删除或迁移前通过隔离索引建立独立检查点，核对原索引摘要不变。
- 产物：起始基线记录、检查点 ref、任务状态清单。检查点保存当前授权范围内的源码，不包含凭据或运行时用户数据。
- 验收：能定位阶段前状态；没有 reset/clean、误暂存或覆盖其他来源修改。数据备份与源码检查点分别管理。

### P0.2 修复 lint 与死代码检查覆盖（G01、D06、G02）

- 文件：`eslint.config.mjs`、`knip.json`、`package.json`、七处后端未用符号所在文件。
- 动作：将当前 backend/contract 纳入 JS 规则；继续排除生成 registry。contract 的旧未执行工厂先按 P4.3 清掉或在同一提交中处理，不用全局声明 webUtils 掩盖问题。
- 动作：删除确认未使用的绑定和私有函数，保留 await/初始化表达式副作用；核对性能测试能从根 CI 入口到达。
- 动作：明确根 Knip 当前只配置根 workspace，不能据此宣称 Runtime 和 Bridge 已全覆盖。为相关包建立独立扫描范围；动态 Cordis、生成入口和类型引用逐项说明例外，不整目录静默忽略。
- 验收：backend/contract 中注入未用变量或未绑定标识符会被规则识别；Knip 能识别一个无消费者样例。临时探针验证后移除，不引入无用途测试文件。

### P0.3 建立源码回归和性能基线

- 当前根 semantic-search 脚本导入 `lib/types/*.js` 及包入口，不能单独证明最新 TS 源码已修复。
- 新算法断言首先执行当前源码；另保留正式包入口烟测。修改 Runtime 后使用受影响包的正式构建链重新生成必要产物，再执行包入口验证，不手工修 lib。
- 拟新增统一入口 `test:performance-regressions`，只放行为、次数和容量等确定性断言；拟新增 `benchmark:code-hotpaths`，输出当前源码的规模/耗时对比。名称以实施时现有脚本为准，避免重复入口。
- 基线输入：Markdown 1k/2k/4k/8k 行；8 个并发冷请求；聊天 100/500/1,000 轮及对应工具行；FTS 1k/10k 事件；会话正文总量 1/10/50 MiB；usage 100/1k/10k buckets。
- 产物：`docs/benchmark-results/` 下的基线 JSON、运行方式、Node/pnpm/提交信息、样本数和统计口径。使用合成数据，不写真实提示词、凭据或私有内容。
- 验收：源码与包入口分别有结果；基准可复跑，冷/暖/追加后查询分开记录，耗时测试独占运行。

## 4. P1：先闭合正确性和主要平方扫描

### P1.1 过滤进入向量候选选择（A01）

- 文件：semantic-search 的 `types.ts`、`vector-store.ts`、`searcher.ts` 及对应测试。

- 验收：四 chunk 的 target.ts 复现返回目标；组合 file/language/type、空集、不足 K 条、无过滤、非法 K、非有限分数全部通过。
- 性能：过滤后无需为不合格 chunk 算向量分数；保留有界候选堆，不增加全量排序。

### P1.2 Markdown 切分改为单次状态扫描（A02）

- 文件：`markdown-stream-blocks.ts`、`AgentMessageMarkdown.tsx`。
- 动作：记录 fence、列表缩进、引用、表格和引用链接状态，删除每行重建整个前缀的路径；先完成一次解析的线性化，再做尾块增量处理。
- 约束：只有确认不会再变化的块才能缓存；不把未闭合代码块或跨块引用提前固定。输入回退、重试替换或不是前缀追加时，完整重置解析状态。
- 验收：现有展示断言不变，补长列表、嵌套、空行、表格、引用、代码围栏、Setext 和分片追加/回退。
- 性能：确定性计数证明每行状态处理近似一次；8k 输入不发生平方增长。4k 列表目标单次低于 50 ms，仅作为同机性能目标，不作为跨机器 CI 硬阈值。

## 5. P2：并发合并、传输解析与索引生命周期

### P2.1 工作区索引合并在途构建（A03）

- 文件：`backend/workspace-index.mjs`、工作区上下文定向测试。
- 动作：按 root+generation 保存在途 Promise；成功、失败和切换时明确释放；缓存代际阻止迟到结果污染。结果达到 limit 后停止收集。
- 验收：8 个冷请求只构建一次，3,000 条目 lstat 约 3,000 次而不是 24,000 次；TTL、切 root、失败重试、空工作区及软链接边界通过。
- 此步骤不擅自用 Dirent 替换全部 lstat；路径/软链接安全判断单独保留和验证。

### P2.2 Cursor OAuth 合并刷新（A04）

- 文件：`oauth-token-cache.mjs`、Bridge transport 的 token 获取路径和测试。
- 动作：区分已完成缓存与在途工作；按 provider/凭据代际合并。底层加载使用独立控制器，各等待者独立取消；最后一个消费者退出时才考虑取消底层任务。
- 验收：8 并发只调用一次 loader；单个取消不影响其他请求；失败后能重试；invalidate/clear 后旧工作不回填新代缓存；过期和 401 行为保持一致。
- Google 账户 snapshot 保持独立，不因这次优化混用账户、项目或 token；日志不输出 token。

### P2.3 SSE 增量解析（A05）

- 文件：`google-antigravity-adapter.mjs` 及 Provider transport 测试。
- 动作：增量计数、换行游标和分片收集，完整行结束时合并，移除对未完成长行的重复 split/byteLength。
- 验收：UTF-8 跨片、CRLF、多行 data、空帧、终止、异常、取消和 16 MiB 边界；1/2/4/8 MiB 分片输入的工作量随字节数增长，输出事件顺序不变。

### P2.4 分块预处理和索引容量（A06、A15）

- 文件：semantic-search 的 `chunker.ts`、`index.ts`、embedding/index 生命周期代码。
- 动作：每文件只提取一次 imports；将全局索引移到 Host/插件实例生命周期，增加工作区数量或字节预算及 LRU 淘汰。
- 动作：淘汰在途索引时防止完成后重新注册；被淘汰工作区明确提示重建，不伪装已有索引。provider/凭据变化只失效所属实例。
- 验收：1,000/2,000 函数的 imports 提取均为一次；两实例同工作区互不 reset；多工作区超预算会淘汰；退出/失败/取消能释放，旧完成结果不复活。
- 容量默认值依据 P0 样本测量后固定并说明，不把所有工作区长期留在内存。

## 6. P3：聊天和界面派生数据

### P3.1 一次构建工具分桶和消息关系（A07、A08）

- 文件：`dshTranscriptMessages.ts`、`MainConversation.tsx`。
- 动作：工具按 turn 分桶；消息前后关系用前向/后向遍历构建。渲染行只做索引查询，避免每行过滤或逆向扫描全部历史。
- 验收：turn=0、无 turn、最新行 traces、连续助手、steer、context/compaction、失败、编辑和重试全部保持原归属和锚点。
- 性能：固定工具/消息比例时派生处理近似 O(M+T)；父组件更新不会为每行重新 filter 全部工具。

### P3.2 稳定缓存按当前所有者回收（A09）

- 文件：`stable-callbacks.ts`、`stable-messages.ts`、聊天组件调用处。
- 动作：为缓存增加会话所有者和有效 key 淘汰。优先清缓存而非重挂整个聊天组件；临时会话尚无 conversationId 时，使用稳定 thread 身份隔离，避免多个 null 会话共用缓存。
- 验收：100 次会话切换、回退和删除后，缓存数量受当前有效消息及明确预算约束；旧 callbacks 不操作新会话；有效消息 callback/array identity 保持稳定，滚动和草稿不回退。
- 内存快照用于辅助，确定性容量断言作为 CI 门槛。

### P3.3 模型分组和历史文本恢复（A17）

- 动作：模型按 provider 一次分桶；查询词只筛各桶。保持订阅、自定义、未知来源与 bridge/opencodex 规则。
- 动作：历史恢复先复用已有稳定关联字段；缺少关联时按时间/behavior 建候选索引，保留有序匹配与原始用户文本保护，不新增一套跨 Host 的临时身份协议。
- 验收：全匹配/全不匹配、混合历史、重复文本、10 分钟边界和 steer；没有唯一依据时保留原有安全回退，不能为了提速把内部拼装 prompt 误当用户原文。
- 性能：模型分组 O(P+M)；历史恢复不再对每个明显不相容候选重复做全文 includes，记录最坏重复文本场景的限制。

### P3.4 DAG 展示按图处理（A16）

- 动作：一次建邻接表；共享后继只完整显示一次，其他边提供引用；访问路径检测环和缺失依赖，不扩大后端节点上限。
- 验收：1—12 节点、密集/菱形 DAG、无根、孤立、缺失依赖和损坏环；完整节点视图不超过节点数，引用边规模不超过边数。
- 33 节点等放大输入只作为健壮性实验，不能作为当前正常 12 节点请求的性能结论。

## 8. P5：会话查询增量化

### P5.1 窗口读取只复制返回窗口（A11）

- 文件：session-query 的 index/corpus 及查询测试。
- 动作：为 live 事件增加受控窗口读取路径；已冻结源只在内部借用，对外仍返回独立快照。冷日志维持当前读取约束。
- 验收：10k 事件读取一条时，不 clone 全部事件；返回对象修改不能影响源；seq 边界、空窗、取消和损坏事件返回原错误语义。

### P5.2 FTS 区分 append、replacement 与全量失效（A10）

- 文件：session-query-sqlite 的 observation、文档投影、SQLite 写入及 cursor generation。
- 动作：按 seq 复用 observation。单调 append 只生成新增或受影响文档；surface replacement/删除只更新受影响项；日志身份变化或无法证明可增量时才重建。
- 先在内存 SQLite 中验证，再覆盖文件数据库、重启与持久化服务切换；避免同时改 schema 和日志协议。
- 验收：新增不产搜索文本事件不重写全部 FTS；追加一条时 SQL 写入量随受影响文档变化；搜索、snippet、trace、live 优先和 cursor 失效行为与现有语义一致。
- 必测：append→search 1k/10k、replacement、reset、取消、并发源变化；保留 warmed 10k probe。

### P5.3 冷索引有限并发与快照复核（A12）

- 先把串行 inspect 改为有界并发，沿用已有并发配置或共同校验，取消时停止派发新任务。
- 再为 JSONL 增加可验证的 snapshot/header 缓存；未改变文件可复用，未知/外部变化时保守回退扫描。跨进程变化不能只靠内存事件通知。
- 保留前后快照一致性复核与重试上限，不为了减少目录读取直接删掉第二次观察。
- 验收：并发数有界，损坏日志和取消明确失败，变化期间不交付混合版本；分别记录冷启动、暖查询、修改一个日志的 I/O 次数与耗时。

## 9. P6：usage 与会话存储

此阶段单独审查恢复语义，不与缓存或死代码提交混在一起。

### P6.1 usage 目标 bucket 更新（A14）

- 动作：先消除每条 record 的重复全量聚合/排序；规范化与迁移时聚合，运行时按 key 更新，展示/导出时排序。
- 持久化队列内维护正确失效的索引，不能在每次读取新快照后继续使用旧数组索引。保留当前 record Promise 的持久化完成语义，不引入未经约定的丢失窗口。
- 验收：跨日、幂等、禁用、并发、迁移和落盘失败；结果与旧格式兼容。明确记录 JSON 全量写成本仍存在，不把局部 O(1) 更新说成完整存储 O(1)。
- 若基线证明 JSON 写入已成为主要耗时，再在独立提交中采用按月分片；涉及报表/清空/迁移的全链路另行验收。

### P6.2 会话小更新先去掉冗余全文件读取（A13第一步）

- 动作：利用事务返回结果形成当前 UI 状态，避免 updateConversation 写完后再 read 同一完整文档；必要缓存有明确代际和失效规则。
- 约束：保持共享队列、错误隔离和持久化完成语义；不缓存尚未提交的状态，不把 JSON rename 当跨进程锁。
- 验收：同一次更新读写次数下降，两个 store 实例并发不丢更新，当前会话/摘要/正文返回一致；fork、归档、删除及损坏恢复通过。

### P6.3 会话摘要与正文拆分（A13第二步）

- **已选 SQLite，而非双 JSON 文件。** 摘要索引和正文保存在同一个 `taskweaver-threads.sqlite` 数据库中：`thread_summaries` 保存导航字段，`thread_bodies` 按会话隔离正文，`store_meta` 保存版本与当前会话。WAL、`synchronous=FULL`、10 秒 busy timeout、外键级联和 `BEGIN IMMEDIATE` 事务提供跨连接/跨进程协调；不以进程内 Promise 队列或多文件 rename 充当事务。
- **读取范围。** 列表和搜索只读取摘要；更新读取并写入目标正文/摘要。正文保留一代上一版已提交内容；损坏时显式报错，只有用户/运维明确执行恢复命令后才恢复上一版，不静默改写。
- **写入边界。** 桌面 compose 创建一个 `AppStateStore`，IPC 与同进程定时任务通过该实例写 UI ThreadStore；独立 Node 进程仍由 SQLite 事务协调。Z Runtime 的权威 session event JSONL 是另一条存储链，由 `PersistenceCoordinator` 和 JSONL backend 管理，本次迁移不替换它。静态写入清单是回归 tripwire，不是对动态 alias 或任意变量路径的完整程序分析。
- **迁移。** 支持 V1 单体 JSON、V2 摘要加 `threads/<id>.json`、旧 `taskweaver-app-state.json`，并可将旧 SQLite schema v1 升级到 v2。旧源文件保留原字节并独立备份；SQLite 数据与 schema 标记同一事务提交前校验 ID、数量、消息/tasks/logs 与摘要。失败事务可重试，源文件不删除。
- **回退与修复。** `pnpm run export:thread-store-rollback -- "<USER_DATA_DIR>" "<OUTPUT_JSON>"` 独占创建完整 V1 快照，拒绝覆盖；旧版写入前停止所有写入者并保留原 SQLite 文件组。`pnpm run recover:thread-store -- "<USER_DATA_DIR>" "<CONVERSATION_ID>"` 仅在正文损坏且上一版可验证时显式恢复。SQLite 页级损坏或当前/上一版都不可解析不由该命令修复。
- **当前证据。** `node scripts/test-thread-store-split.mjs` 覆盖 V1/V2 导入、备份、SQLite v1 升级、四进程并发首次迁移、事务失败回滚/重试、正文损坏恢复、fork/delete 和完整导出；4 进程并发首次迁移在三轮并行压力复测中通过。`pnpm run test:threads` 覆盖 48 次真实双进程追加与目标正文局部更新。`pnpm run benchmark:thread-store` 记录 1/10/50 MiB、5 次预热/20 次采样：V1 JSON p50 3.90/34.09/172.66 ms，SQLite p50 0.139/0.117/0.108 ms。详细迁移与回退步骤见[会话 SQLite 迁移说明](/Users/zsn/Documents/毕设/docs/会话 SQLite 存储迁移与回退说明-20261030.md)，原始数据见 [`thread-store-2026-10-30.json`](benchmark-results/thread-store-2026-10-30.json)。
- **限制。** 全量集成门槛已分别在 Node v22.23.1 与最低支持版本 v22.18.0 运行；`node:sqlite` 会发 experimental warning。应用产物内 Host Node 是 v22.19.0（满足 `>=22.18`），该版本通过 ThreadStore 迁移和 stdio RPC 两组定向回归。单会话恢复槽仅保留最近一版；静态 writer 清单不证明任意动态/计算路径。
- **状态：** 核心迁移、显式恢复和确定性故障/并发验证完成；2026-10-30 全量集成门槛已在 Node v22.23.1 与 v22.18.0 通过。真实用户数据迁移仍未实测。
