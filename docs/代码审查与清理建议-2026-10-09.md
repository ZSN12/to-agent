# TaskWeaver 代码审查与清理建议

审查日期：2026-10-09。基于当前工作区实际文件，包含已有未提交修改。此次仅新增本报告，没有修改或删除业务代码。

## 结论

目前最需要处理的是：Z Runtime 迁移后遗留的接口断链、打包资源遗漏、重复的会话状态及测试实现。单纯删除几个未使用变量，收益有限。

建议顺序：先补齐接口与打包闭环，再删除明确没有消费者的代码，最后按职责拆分前后端大文件。DAG、模型路由、Host 会话、安全策略和 Git/worktree 是项目核心能力，应保留并理清边界。

## 一、优先修复的功能断链

### 1. preload 暴露了 5 个未注册的 IPC 通道

将 `electron/preload.cjs` 中 148 处 invoke 调用与 `electron/` 中主进程注册对照，以下通道缺少 handler：

| 通道 | 当前消费者 | 建议 |
| --- | --- | --- |
| `chat:listRunningConversations` | `useAppBackend.ts:345`、`:362`；初始化及每 5 秒同步 | 补齐注册，返回真实运行会话，包含必要的编排状态 |
| `worktree:previewMerge` | `WorktreeMergeActions.tsx:16`、`:46` | 接入已有 `previewTaskWorktreeMerge`，保留工作区操作互斥和路径验证 |
| `worktree:applyMerge` | `WorktreeMergeActions.tsx:65` | 接入已有 `applyTaskWorktreeMerge`，保留忙碌状态、冲突及授权检查 |
| `permission:listApprovalAudit` | preload 与类型定义；当前无界面调用 | 明确是否保留审计功能；保留则同时接通写入和查询，否则删除空接口 |
| `models:resolve` | preload 与类型定义；未发现当前界面调用 | 若无消费者，删除 preload/API 声明；否则注册已有模型解析方法 |

前三项是现有界面真实调用，不能按“后端函数只被测试使用”删除底层实现。缺少 handler 时，`ipcRenderer.invoke` 会拒绝 Promise；它没有进入 `ipcHandle` 的错误封装，不能指望拿到 `{ ok: false }`。运行状态同步和合并按钮会因此失效，调用处也缺少对应的异常兜底。

验证：`node scripts/test-worktree-diff.mjs` 通过，说明底层合并逻辑有测试；这并不覆盖界面到 IPC 的连接。需要补一项 preload 通道与注册表的一致性检查，再加关键功能的桌面调用测试。

### 2. 打包漏掉运行时桥接支持目录

位置：`electron-builder.yml:29`，`scripts/build-host-runtime.mjs:419`，`electron/agent/z-host/spawn-host.mjs:26`。

构建脚本主动生成：

```text
vendor/taskweaver-z-runtime/electron-vendor/taskweaver-bridge-transport/
vendor/taskweaver-z-runtime/electron-vendor/dsh-client-runtime-lib/
```

但 `extraResources.filter` 只包含 lib、config、runtime-packages、客户端及元数据，没有 `electron-vendor/**/*`。用当前过滤规则核对，以上两个真实存在的文件均被排除；现有 `release/mac-arm64/TaskWeaver.app/Contents/Resources/taskweaver-z-runtime/` 也没有 `electron-vendor/`。

其中 bridge transport 是 Host 加载 TaskWeaver 模型桥的入口；SessionManager 的支持目录是主进程加载路径之一。源码目录可通过相邻仓库路径回退，独立安装包无法依赖这类回退。应把实际需要的支持文件加入资源清单，并在搬离源码目录的包内验证模型桥及主进程对话投影。SessionManager 是否还能从 runtime-packages 回退，需要包内实际加载确认；不能仅因缺少支持副本就断言所有投影必然失败。

另一个构建缺口：`build-dsh-chat-registry.mjs` 只作为单独 npm 命令存在；当前 `build:z-runtime` 与 `make-mac-app.sh` 没有自动调用它。已有 `electron/vendor/dsh-chat-registry.mjs` 会被打包，但修改投影源码后可能仍打入旧 bundle。应纳入统一构建依赖或增加来源哈希验证。

### 3. “会话写入清单”测试当前失败

执行 `node scripts/test-conversation-single-writer.mjs` 得到：

```text
register-ipc.mjs | appendMessagesToConversation:conversationId,{
expected 1, found 4 (lines 498, 537, 578, 1620)

register-ipc.mjs | upsertMessagesToConversation:conversationId,{
expected 0, found 1 (line 1607)
```

这是当前工作区的真实基线失败。该测试本身明确只做写入点清单，不证明已经只有一个权威写入者。应先确认定时任务和失败处理新增写入点的职责，再更新清单；不要仅修改预期数字使其通过。

## 三、架构优化建议

### 1. 拆分 App 与后端总注册器，先按现有职责移动

| 文件 | 当前行数 | 拆分方向 |
| --- | ---: | --- |
| `src/App.tsx` | 5,097 | AppShell/导航、Sidebar、Composer、Conversation、UsageSettings、Task/DAG 面板 |
| `src/features/app/useAppBackend.ts` | 1,406 | 线程操作、会话运行状态、权限与问题队列、投影订阅、Skill 目录 |
| `electron/backend/register-ipc.mjs` | 1,961 | 创建服务的启动编排；chat/models/permissions/worktree/preferences 等领域 IPC |
| `electron/backend/dsh-chat-service.mjs` | 2,343 | Host 连接恢复、session 映射、turn 生命周期、审批/提问、用量快照与事件适配 |
| `electron/backend/model-service.mjs` | 1,211 | 模型目录、凭据与授权、提供方发现、Host 同步 |

已有 `register-terminal-ipc`、`register-workspace-git-ipc`、`register-scheduled-jobs-ipc` 可作为拆分样例。先移动代码、保持行为，再改接口和状态模型，降低迁移过程中同时改变多条链路的风险。

### 2. 统一 IPC 声明来源

同一个 API 现在分别存在于 TS 接口、preload、主进程 handler，已经出现五处不一致。建议建立领域通道表，生成或校验 preload 与类型，并让测试比较实际注册的通道，而不是只测试底层函数。

桌面 shell 负责组装服务；业务服务无需直接知道 BrowserWindow。后续可逐步注入事件发布器，集中处理 conversationId、taskId 和 turnId，避免每个服务各自适配 Electron 事件。

### 3. 会话状态与持久化要定义唯一职责

现有数据至少分布在 Host session log、DSH 对话投影、TaskWeaver threads JSON、前端 stream buffer、usage ledger。

这些并非全部重复：TaskWeaver 的编排说明、失败提示、线程元数据不能直接由 Host transcript 还原。因此应定义：Host log 保存原生会话事实；threads 保存 UI 专属元数据和必要扩展；前端 buffer 只承载尚未提交的实时内容；usage ledger 保存记账事实。对同一 turn 的终态、失败和用量统一提交入口，以 turnId 做幂等。

现在 `chat-turn-persistence` 和 register-ipc 仍同时处理终态消息；`useAppBackend` 还合并存储消息与 DSH transcript。这是最值得逐步收敛的状态复杂度来源，不能直接清空 threads 消息实现“去重”。

### 4. 删除前端只写不读的 mux 缓冲，保留必要订阅

`useAppBackend.ts:127` 的 `dshMuxTapeRef` 只在 `:418–419` 写入、裁剪，没有读取；最多保存 800 个原始帧。可删除该 ref 和专用 onMux listener。

进一步停止原始 `chat:mux` 向 renderer 复制也有收益，但应保留 Host → conversationHub 的处理。尤其不能直接删除 `subscribeMux/unsubscribeMux`：当前它们还负责 attach/detach 主进程投影，会影响 `chat:dshView`。先把“订阅对话投影”和“订阅调试原始帧”拆成独立职责，再去掉无人消费的原始 IPC 数据。

### 5. 测试必须引用实际生产策略

当前压缩策略存在两份：

```text
src/shared/context-compaction-policy.ts          ← 界面使用
electron/backend/context-compaction-policy.mjs ← 测试使用
```

显示策略也有相同问题：

```text
src/shared/transcript-display-policy.ts          ← 界面使用
electron/backend/transcript-display-policy.mjs ← 测试使用
```

压缩提示文字已经不同。这些测试通过，只能说明镜像实现符合断言，不能证明界面实现正确。建议将纯策略收敛为一个共享模块，通过受控的 TS 编译/测试加载方式运行；随后删 backend 镜像。不要保留两份逻辑再依赖人工同步。

### 6. 持久化队列应在 store 层统一

`json-store.mjs` 已有按文件路径共享的更新队列，但 `thread-store.mjs:79` 仍采用独立实例队列中的 `read → mutator → write`，没有调用 `store.update`。两个 ThreadStore 实例对同一文件操作时，读改写整体不互斥。

本次在临时目录复现：创建两个 ThreadStore，分别并发重命名两个不同线程，最终只保留一个重命名，`both updates persisted false`。当前桌面主路径只找到一个 AppStateStore 创建点，因此这是已复现的多实例能力缺口，不代表普通单实例操作一定丢数据。

建议改为 `store.update` 统一事务；若桌面与系统调度器等不同进程确实共享同一数据文件，还需单独解决跨进程互斥，不能把原子 rename 当成读改写事务。

随着线程增长，整个 threads JSON 每次全量读取、解析和重写也会扩大成本。可先拆线程索引和每会话扩展数据；再根据实测决定是否迁移 SQLite，无需为了架构形式立即更换存储。

### 7. 模型初始化改成有序启动流程

`register-ipc.mjs:158–235` 启动多个独立 Promise 链：旧配置迁移、默认模型写入、Host 启动同步、旧路由迁移及目录刷新，部分操作落到相同模型配置和 Host。

这是顺序难以推断和潜在竞争的来源，本次未复现具体启动丢失。建议定义明确的 bootstrap：迁移/默认配置准备 → Host 就绪 → 同步模型 → 路由迁移及桥接目录刷新 → 对外发布 ready 状态。用同一个 in-flight Promise 合并并发调用，区分必要初始化与可后台执行的目录更新。

### 8. 清理配置和打包流程的重复

- `vite.config.ts` 的 closeBundle 与 `scripts/strip-html-crossorigin.mjs` 做相同替换，build 两处都执行。保留一个权威步骤，并用产物检查验证。
- `config.mjs` 的 CONFIG 聚合对象没有消费者；部分默认值只在该对象中使用。删除无用聚合，配置归到真正的拥有者，避免常量与模块实际默认值两套来源。
- `npm run app` 会准备 runtime，`app:builder` / `app:dmg` 主要构建 UI 后直接打包，前置条件不一致。统一 package 流程，让所有入口都校验 runtime、registry、bridge 和元数据。
- 根目录同时存在 npm/pnpm lockfile，而 CI 主要 npm ci、vendor 内又独立 pnpm。应明确根应用与 vendor 的包管理器范围；确定根应用使用 npm 后再移除冗余根 pnpm 配置/锁，不删除 vendor 自己的锁文件。
- `tsconfig.app.json:20` 排除一个已不存在的 DiffViewer 文件，是旧构建豁免，建议删除。

### 9. CSS 与测试脚本组织

`styles.css` 9,727 行，`styles-dsh-parity.css` 2,352 行，且两者都由 main.tsx 引入。建议按 shell/chat/composer/settings/tokens 分域整理，记录层叠顺序。动态 className 和覆盖规则很多，不能仅凭文本搜索零引用就删除 CSS。

## 四、文件体积清理

实测目录大小：release 约 2.4G、根 node_modules 约 2.4G、.pnpm-store 约 1.4G、packages/runtime/node_modules 约 1.4G、deploy runtime 约 244M、dist 约 1.4M。它们包含依赖和构建输出，**不是未使用业务代码规模**；pnpm 链接及共享存储可能导致大小不可简单累加。

- dist、过期 release 产物、tsbuildinfo 可在确认重建路径后清理；根 TaskWeaver.app 是指向 release 的链接，清理 release 会影响它。
- deploy runtime 是桌面运行/打包的现有输入，不能一边使用一边按缓存删除。
- node_modules 和 pnpm store 可重建，但删除后需要重新安装；不属于本次代码删除建议。
- 顶层 `vendor/taskweaver-dsh-client/` 只有一份旧 web-api-client.js，仍引用缺失的同目录 api.js；当前客户端解析从 runtimeRoot 内寻找，未发现读取这个顶层旧目录的路径。可作为旧产物清理候选，先更新历史说明，不要删除 deploy 内正常客户端。
- vendor 源码中的 website/docs/examples 不是桌面直接入口，但可能属于上游测试、构建和同步流程。应先验证工作区及构建引用，再决定从应用分发剔除或从源码仓库移出，不能整树盲删。
- 根 dependencies 中列出的包均找到当前运行时或界面的 import/require；未发现可直接删除的根生产依赖。
